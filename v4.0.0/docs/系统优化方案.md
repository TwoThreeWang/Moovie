## 一、先说结论

系统不是设计错了，是**每件事都多做了一层**。

打个比方：这套系统像一个家里买了 6 个不同牌子的烧水壶，
每个壶单独看都没毛病，但你其实只需要一个。

体检下来是三类问题，按「改了最划算」排序：

| 类别 | 具体是什么 | 占多少 |
|---|---|---|
| **有 BUG 没发现** | ① 统一搜索一条 SQL 少写了 JOIN，「补充资源」一直是关的；② 豆瓣卡片点进去 302 弹回搜索页（**已修**） | 2 处 |
| **做了没人用** | 1 张表只写不读、1 套刷新阶梯算完就扔 | 约 1～2 张表 + 100 行 |
| **同一件事做了好几遍** | 复核后真重复的只剩：1 份缓存、1 份限流、2 个播放模板 | 约 300 行 |

**这三类加起来，能删掉大约 400～550 行代码和 1～2 张表，功能一点不少。**

比初版说的「2000～2500 行」少了一大截——因为初版把很多**长得像但职责不同**的东西
错当成了重复（见上面的复核说明）。剩下的 2 万多行确实是真在干活的，不建议大动。

### 一句话建议

**不要重写，按批次删。** 分 5 批，每批做完都能单独上线，
哪一批不想做就跳过，不影响后面。

## 三、五个批次

### 批次 0：修两个 BUG（1 天，必做）　✅ **已全部完成**

#### BUG 1：统一搜索的 SQL 少了一个 JOIN　✅ **已修**

**问题**：`internal/search/unified_postgres.go:58` 的 `ListUnifiedResources`，
SQL 里要读 `media_link` 这张表的三个字段，但 `FROM` 里根本没写这张表。

**我做了什么验证**：连真库跑了这条 SQL，数据库直接报错：

```
ERROR: missing FROM-clause entry for table "media_link" (SQLSTATE 42P01)
```

**造成的后果**：`internal/search/unified.go:141` 每次统一搜索都会调它，
每次都失败 → 代码判断「资源查询出错了，走降级」→
**「补充资源」这条路永远走不通，用户永远看不到那部分结果。**

**怎么改**：那条 SQL 的 `FROM` 里加上已有的 `resourceMediaLinkJoin`，**一行**。
这个变量就在隔壁 `internal/search/postgres.go:49`，别的查询都在用，只有这条漏了。

> 这个 BUG 也解释了一件事：如果你之前觉得「搜索结果好像少了点什么」，
> 不是错觉。

**实际怎么改的**：没有加 `resourceMediaLinkJoin`，而是把它已经 JOIN 的
`resource_media_links` 的别名直接改成 `media_link`——那条 SQL 本来就 JOIN 了这张表，
再叠一个 LATERAL 等于同一张表查两遍。`resource_media_links` 的主键是
`(source_key, vod_id)`，直连不会把行数放大。

**为什么这个 BUG 能活这么久**：`internal/search/postgres_test.go` 用的是一个
**假数据库**（`fakeSQLDatabase`），只对 SQL 字符串做子串匹配，根本不连真库，
所以一条语法都跑不通的 SQL 也能「测试通过」。这次补了
`TestListUnifiedResourcesRunsAgainstTheRealSchema`，连真库跑；
把修复回退掉重跑，它确实会红。

#### BUG 2：豆瓣卡片点进去被弹回搜索页　✅ **已修**

**现象**（你反馈的）：搜索结果页的豆瓣卡片显示「在线播放 · N 个来源」，
点进去却 302 弹回搜索页；等一会再点就正常了。

**根因**：卡片和 `/watch` 用的是**两套完全不同的判断**。

| | 判断依据 | 在哪 |
|---|---|---|
| 卡片说「有 N 个来源」 | `vod_items.vod_douban_id = 豆瓣ID` | [unified_postgres.go:81](internal/search/unified_postgres.go:81) |
| `/watch` 能不能播 | `resource_episode_candidates.media_id = 媒体ID` | [handler.go:694](internal/playback/handler.go:694) |

卡片这个条件宽松得多——它自己的注释就写着「不依赖 `resource_media_links` 是否已经回填」。
所以卡片能显示，不代表 `/watch` 能播。

**为什么「等一会再点就好了」**：那个 302 是跳到 `/search?kw=片名`，
这一跳本身又触发了一次完整搜索，而这次搜索把索引补上了。
**是这次失败的跳转自己把问题修好的。**

索引只有两个地方会写：搜索时（[search_adapter.go:39](internal/mediaidentity/search_adapter.go:39)）
和用户访问 `/play` 时（[handler.go:548](internal/playback/handler.go:548)）。
`/watch` 自己从不建索引——它的注释说「Worker 处理资源时」也会建，
**但我查了，没有这个 Worker，这句注释是过期的。**

你的判断基本对：关联先落库，索引晚一步。具体有两条路径都会造成这个时间差：

1. **卡片和搜索是两个并行的 HTMX 请求**
   （[search.html:22](web/templates/pages/search.html:22) 和 [:38](web/templates/pages/search.html:38)）。
   卡片只读 `vod_items` 所以先回来，写索引的是慢的那个搜索请求。手快就点空了。
2. **`fetchAndSave` 里先建索引、后建关联**
   （[service.go:415-421](internal/search/service.go:415)）。
   新资源第一次被索引时关联还不存在，索引写进去的 `media_id` 是空的。
   正常情况下紧接着的 `LinkResource` 会回填，
   但如果关联已经存在（走了第 0 层缓存命中），`LinkResource` 不会被调用，
   **也就没人回填**，只能等下次搜索重新索引。

**怎么改**（一处，约 12 行）：`/watch` 在 `len(ranked) == 0` 要 302 之前，
先看 URL 上有没有 `source_key` 和 `vod_id`——豆瓣卡片**本来就传了**
（[douban_card.html:105](web/templates/partials/douban_card.html:105)）。
有的话就按 `/play` 的做法直接取详情播，顺手把索引补上。

`/watch` 现在是拿到了这两个参数、但在用到它们之前就 return 了
（[handler.go:703](internal/playback/handler.go:703) 的 302 在
[:711](internal/playback/handler.go:711) 读 `source_key` 之前）。
**它需要的信息一直在手里，只是没用。**

> 顺带说：详情页用的是另一个函数 `HasPlayableResource`，
> 那个判断是**对的**（注释写着「与 /watch 的输入保持一致」）。
> 只有搜索页的卡片没用它。

#### 顺带发现：一条会让测试随机变红的时钟问题（不是线上 BUG）

跑测试时 `internal/workqueue` 会**时好时坏**。查出来的原因是：

- 入队时，`available_at` 用的是**本机时间**（[queue.go:112](internal/workqueue/queue.go:112) 的 `time.Now()`）；
- 领任务时，判断条件用的是**数据库时间**（[queue.go:140](internal/workqueue/queue.go:140) 的 `available_at <= NOW()`）。

我在你这台机器上量了一下：**数据库的钟比本机慢约 60 毫秒**。
于是「刚入队就领」的那一瞬间，任务在数据库眼里还没到点，领不到。

**线上没影响**（Worker 是轮询的，慢 60 毫秒下一轮就领到了），
但测试是「入队完立刻领」，所以会随机失败。

**怎么改**：入队时别用本机时间，让数据库自己填——
`available_at` 传 NULL、SQL 里写 `COALESCE($8, NOW())`。**改一行，两边的钟就统一了。**

> 这条不算在下面的批次里，因为它不删代码，纯粹是让测试稳定。

### 批次 P：页面打开了但内容要等一会（已完成，不在原方案里）

你反馈的「页面打开了、内容还在转圈」不是错觉，也不是网络问题。
逐个接口查下来，慢的全是 `hx-trigger="load"` 那些片段，
而且都卡在**同步等一个可能很慢的外部依赖**上。下面五条都已经改完并有回归测试。

#### P1：搜索最长能等 30 秒才出结果

**原来**：`internal/search/service.go` 的 `Search`，只要配了上游资源站，
本地明明已经有结果，也要**同步等**一次上游刷新，预算是
`SEARCH_TOTAL_TIMEOUT_SECONDS=30`。只要有一个资源站卡住，搜索片段就转 30 秒。

**改成**：本地有结果时，最多再等 `SEARCH_REFRESH_WAIT_SECONDS`（默认 3 秒）。
等到了就合并，等不到就先把本地结果还给页面，
**刷新用 `context.WithoutCancel` 脱离请求，继续在后台跑完并写库**——
所以新资源不会丢，只是晚一次搜索才出现。

#### P2：一两个字的关键词能把数据库拖垮

**原来**：`internal/search/postgres.go` 的 `Search` 是
`LIKE '%关键词%'` 查三列、**而且没有 LIMIT**，后面还挂了两个 LATERAL——
其中一个要为**每一行**做一次播放质量聚合（三张表 JOIN + SUM）。
搜「爱」这种一个字的词能命中几万行 `vod_items`，
几万次聚合 + Go 侧几万次媒体身份补全，页面就是转几十秒。

**改成**：先在子查询里筛选、排序、截断到 `searchRowBudget = 300` 行，
**再**挂那两个 LATERAL。页面最多只渲染 20 组，300 行绰绰有余。

#### P3：搜索热路径缺索引（新增迁移 0043）

查了一遍 `pg_indexes`，`vod_items` 上**没有任何**能支撑
`LIKE '%关键词%'` 的索引，也没有 `vod_douban_id` 的索引；
`playback_quality_rollups` 也没有以 `candidate_id` 打头的索引，
偏偏上面那个 LATERAL 每行都要按 `candidate_id` 查它。

`0043_search_hot_path_indexes.sql` 补了 5 个索引：
`vod_name` / `vod_sub` / `vod_en` 三个 pg_trgm GIN 索引、
`vod_douban_id` 的部分索引、`playback_quality_rollups (candidate_id, bucket DESC)`。

> pg_trgm 早就装好了（迁移 0019），`media_aliases` 一直在用同样的写法，
> 所以这不是引入新东西。
>
> ⚠️ 迁移是在**一个事务**里跑的，所以用不了 `CREATE INDEX CONCURRENTLY`。
> 建索引期间会短暂挡住 `vod_items` 的**写入**（读不受影响）。
> 表大的话建议挑低峰期部署。

#### P4：发现页冷启动要等 10～20 秒

**原来**：`internal/catalog/douban.go` 的 `Popular` 缓存 12 小时，
但缓存一过期，**下一个打开发现页的人就要替所有人去豆瓣取一次**。
主接口超时 10 秒，失败还要再走 Rexxar 兜底又一个 10 秒——最坏 20 秒的加载圈。
重启进程后缓存是空的，那一波用户全中招。

**改成**：缓存过期但旧榜单还在，**先把旧榜单还给页面，刷新丢到后台**
（stale-while-revalidate）；刷新走 singleflight，
四个分类同时被打开也只发一次请求。只有完全没缓存的冷启动才同步等一次。
热门榜晚几分钟没人看得出来，但等 20 秒的用户一定会走。

#### P5：搜索页的豆瓣卡片没超时也没限流

**原来**：`internal/catalog/handler.go` 的 `doubanCard`，
本地匹配不足 5 条就直接调豆瓣的联想接口，用的是**公用的 10 秒超时** HTTP Client，
**而且绕过了 `provider.limiter`**（`Fetch` 走了限流，`SuggestExternal` 没走）。
冷门关键词几乎每次都会触发它。

**改成**：给它 2 秒预算（`externalSuggestBudget`），超时就只显示本地匹配，
下次搜索会再试；同时让 `SuggestExternal` 也走 `limiter.Wait(ctx)`，
不然迟早被豆瓣 429，而 429 之后**所有**豆瓣抓取会一起变慢。

#### P6：搜索结果缓存太小（只改了配置）

`SEARCH_CACHE_ENTRIES` 原来是 200。播放页每换一个线路都会生成一个新的缓存键
（键里带 `exclude=来源:资源ID`），200 条很容易被挤掉，一挤掉下次就要重跑整个搜索。
默认值调到 500，一条大约几十 KB，多占几十 MB 内存。嫌费内存就调回去，纯配置。

#### 顺带修的：任务队列有几十毫秒领不到任务

`internal/workqueue/queue.go` 的 `Enqueue` 原来用**本机时间**写 `available_at`，
而 `Claim` 的判断是 `available_at <= NOW()`（**数据库时间**）。
本机比数据库快几十毫秒，刚入队的任务在数据库眼里就还没到点。
改成不填就交给数据库的 `COALESCE($8::timestamptz, NOW())`，两边用同一个时钟。

> 这个是被测试逼出来的：本地数据库时钟比客户端慢约 60 毫秒，
> 队列测试因此一直红。线上如果 app 和数据库不在同一台机器，同样会踩。

#### 已经确认**不用**改的

| 查过的地方 | 结论 |
|---|---|
| gzip 压缩、静态资源缓存头 | `internal/platform/httpserver/server.go` 里都已经有了 |
| `/api/htmx/reviews`、`/api/htmx/movie-backdrops` | 只读库 + 入队后台任务，不等上游，写法是对的 |
| `/api/htmx/similar`、`/api/htmx/movie-comments` | 纯查库且有条数上限，还带 5 分钟缓存 |
| `/api/htmx/foryou`、`today-updates` | 纯查库 |

#### 1.2 拆掉 `media_source_snapshots` 里那套白算的刷新节奏　✅ **已完成**

> **修订**：初版说「刷新阶梯算完没人用」，说大了。
> 系统里其实有**两套**阶梯，一套真在用，另一套才是死的。

| 阶梯 | 写在哪 | 有没有人读 |
|---|---|---|
| `media.next_refresh_at`（当年片最多 3 天、去年片最多 7 天） | [store.go:593](internal/mediaidentity/store.go:593) | **真在用**，调度器 [refresh.go:124](internal/catalog/refresh.go:124) 读的就是它 |
| `media_source_snapshots.next_refresh_at`（3/7/14/30/90 天） | [store.go:727](internal/mediaidentity/store.go:727) | **零读取** |

（[refresh.go:132](internal/catalog/refresh.go:132) 那个 `+24 小时` 不是覆盖阶梯，
是入队后的占位租约，防止同一部片反复入队；任务跑完会被真正的阶梯值盖掉。
初版把这句读错了。）

所以只有**第二套**是白算的：一套 3/7/14/30/90 天的退避，
算出来写进 `media_source_snapshots`，**从来没有任何代码读过它**。

这张表现在唯一的读取是 3 个 `COUNT(*)` 统计

### 批次 4：收尾（1～2 天，可做可不做）　✅ **已全部完成**

这几条单独看都不大，但都是「越拖越麻烦」的类型：

#### 4.1 `history_sync_events` 会一直涨，且每次同步全表扫　✅ **已完成**

这张表记录多设备同步的事件，**从来没有清理逻辑**。
更要命的是 `bootstrapSyncEvents` 每次同步都要**全表扫一遍**。

用户越多、用得越久，同步就越慢——**这是唯一一条会自己恶化的问题**。

> **2026-08-21 修订**：初版说的改法「`bootstrapSyncEvents` 加时间范围条件」**是错的，别照做**。
> 这个函数存在的意义就是把**早于账本**的老进度补进来，加时间范围正好把它要找的东西筛掉了。
> 代码里原本那句 `ponytail:` 注释建议的「只在游标为 0 时执行」同样不行，原因见下面。

**慢在哪（查清楚了）**：不是「全表扫」，是**每个用户内部的平方级**。
`bootstrapSyncEvents` 靠这个条件反查「这条进度有没有成功事件」：

```sql
NOT EXISTS (SELECT 1 FROM history_sync_events event
            WHERE event.user_id = position.user_id
              AND event.record_id = position.id
              AND event.conflict_reason = '')
```

而这张表只有 `(user_id, version)`、`(user_id, media_unit_id, version)` 和
`(user_id, device_id, operation_id)` 三个索引，**没有一个能用上 `record_id`**。
于是每条进度都要扫一遍该用户的整本账本 —— 代价是「进度数 × 事件数」，
两个数都随使用时间涨，所以是平方级。

**实际做了什么**：

| 改动 | 位置 | 说明 |
|---|---|---|
| 补 `record_id` 反查索引 | 迁移 `0046` | `(user_id, record_id) WHERE conflict_reason = '' AND record_id IS NOT NULL`，把上面那条 NOT EXISTS 从扫账本变成一次索引命中 |
| 补 `created_at` 索引 | 迁移 `0046` | 清理按最旧的一批取，没这个索引清理本身就是全表扫 |
| 保留期清理 | `history.DeleteExpiredSyncEvents` | 留 30 天，分块删（每块 5000 行、每天上限 100 万行），照抄已有的 `DeleteExpiredTelemetry` 写法 |
| 挂到每日清理任务 | `operations.WithSyncEventCleanup` | 复用现成的 `TaskCleanup`（每 24 小时一次），web 和 worker 两边都接上 |

**为什么删旧事件不会丢进度**（这是这条改动唯一需要想清楚的地方）：

进度本体在 `playback_positions` 里，账本只是给客户端增量拉取用的游标流。
某条进度对应的事件被删掉之后，`bootstrapSyncEvents` 那条 `NOT EXISTS` 会重新成立，
**下次同步自动补一条新事件回来**——所以这个清理是自愈的。
也正因为会自愈，账本会稳定在「保留期内的事件 + 每条存量进度一条」，不再无限涨。

反过来说，**正是这个自愈机制要求 `bootstrapSyncEvents` 每次同步都跑**：
按游标跳过的话，被清掉的事件就再也补不回来，老设备会永久收不到那条记录。
所以那句 `ponytail:` 注释里的升级路径已经改写成相反的警告。

**回归测试**：`TestExpiredSyncEventsAreDeletedAndBootstrappedAgain`
（`internal/history/sync_v2_test.go`）——造两条进度，只把其中一条的事件挪到 40 天前，
断言①只删掉过期那条、②下次同步把被删的那条补回来发给了客户端。

#### 4.2 `playback_positions` 的三个唯一索引

> **2026-08-21 修订**：这条也收回，**不要做**。

初版说三个唯一索引是历史遗留、砍掉 `playback_positions_legacy_uidx` 就能把两段 UPSERT 合成一段。
查过之后：这三个是**条件互斥的部分索引**，各管一种身份，谁也替不了谁。

|---|---|---|

| `..._media_episode_uidx` | `media_unit_id IS NULL AND media_id IS NOT NULL` | 关联到片子但没关联到季集 |
| `..._legacy_uidx` | `media_unit_id IS NULL AND media_id IS NULL` | **两样都没关联上的资源** |

第三种不是老数据，是**现在还在天天产生的新数据**：
`upsertPlaybackPosition` 里 `playbackPositionConflictTarget(operation.MediaID)`
是在**运行时**按有没有 `media_id` 选索引的，而
`resolvePlaybackMediaUnit` 的注释白纸黑字写着「实在找不到就返回 0，进度按资源身份保存」。
批次 2 给 `/watch` 加了兜底 `/play` 之后，这条路只会走得更多。

砍掉 `playback_positions_legacy_uidx` 的后果是：**这类进度失去唯一约束，同一集会攒出多行重复进度。**
另外那「两段几乎一模一样的 UPSERT」也不是同一回事——一段要写 `media_unit_id`，另一段不写。

**结论：三个索引全保留，两段 UPSERT 不合并。**

#### 4.3 `search_logs` + `trending_keywords` 可以合成一张

> **2026-08-20 修订**：这条也收回。

两张表**各有各的清理周期**
（[postgres.go:160](internal/search/postgres.go:160) 清 `trending_keywords`，

合成一张之后，日志一到期被清掉，累计热搜数就跟着没了。

**结论：保留两张表，不合并。**

## 五、明确**不建议**动的地方

有些看着「臃肿」，其实是对的，动了会更糟：

| 看着可疑的 | 为什么别动 |
|---|---|
| **每个包一套 Store 接口** | 这是这套代码最健康的地方。接口都很窄，换实现、写测试全靠它。 |
| **`workqueue` 只有一张 `worker_jobs` 表** | 全站所有后台任务共用一张表和一个调度器，已经是很省的做法了。豆瓣同步都没有单独建表，直接复用它。 |
| **42 个 migration 文件** | 数量多是正常的，它就是一部历史。别去合并已经跑过的 migration。 |
| **9 个包各用 singleflight** | 它是小工具不是基础设施，各用各的比统一封装更清楚。 |
| **模板 71 个 / 12000 行** | 除了播放页那两个，其余没有明显重复。服务端渲染 + HTMX 这套本身没问题。 |
| **整体架构（单体 + Gin + Postgres）** | 这个量级的站，这套就是最省心的。别拆微服务，别换框架。 |
| **两套播放页 `/play` + `/watch`** | 分工是对的：`/play` 服务关联不上豆瓣/TMDB 的资源，`/watch` 服务关联上的。缺的是兜底，不是该合并。 |
| **`catalog/douban.go` 那份缓存** | 它**故意返回过期数据**给上游挂掉时兜底。换成通用缓存（一过期就删）会把这个兜底拆掉。 |
| **`outbound.Limiter` 和访问日志限流器** | 一个「排队等」、一个「超了丢」，名字像、行为完全相反。合并会直接改坏功能。 |
| **`discoverPopularAdapter`（10 行）** | 它是防止 `catalog` 和 `playback` 互相 import 的适配器，写在装配根里正合适。删了反而要多开一个包。 |
| **`search_logs` + `trending_keywords`** | 清理周期不同，且后者存累计计数。合表之后日志一到期，累计热搜就没了。 |

**还有一条：别重写。**
你的直觉「写得太复杂」是对的，但复杂来自「多做的那一层」，
不是来自架构选型。删层比重写省 10 倍力气，风险也小 10 倍。

### ⚠️ 跑测试前必须先停掉本地服务

排查队列测试偶发失败时发现的，**这个比上面任何一条都重要**：

你本机现在开着两个进程（`go run cmd/web/main.go` 和 `go run cmd/worker/main.go`），
它们连的是 `.env.local` 里那个 `moovie_v2`，**而测试用的是同一个库**。

后果有两个方向：

1. **测试会把你的本地数据清光。** `testdb.Pool` 每个顶层测试都会
   `TRUNCATE ... RESTART IDENTITY CASCADE` 所有业务表。
   本地库现在 34 张表全是 0 行，就是这么来的。
2. **你的服务会把测试搞挂。** worker 的调度器会在测试跑到一半时
   往 `worker_jobs` 插任务（抓到的是 `imdb_backfill/global`），
   队列测试就领到了别人的任务，随机变红。上面那次全量测试里
   `TestDispatcherHonorsConfiguredConcurrency` 和
   `TestPostgresStoreRecoversExpiredLease` 就是这么挂的——
   单独跑这两个测试 12 次全绿。

**怎么办**（选一个就行）：

- 跑测试前先把两个 `go run` 停掉；或者
- 给测试单独开一个库，`.env.local` 里的 `DATABASE_URL` 指向它
  （`testdb` 只认 `.env.local`，不影响 `.env`）。

第二个更省事，一劳永逸。

### 建议的动作顺序

1. **先把测试库和本地服务分开**——这是唯一还没做的事，也是唯一还会咬人的事。
   （每次全量测试都会清空你本地库；你的 `go run` 也会随机把队列测试搞红。）
2. 迁移 `0046` 会在下次启动时自动跑，加两个索引。
   `history_sync_events` 存量大的话，这条 `CREATE INDEX` 会短暂锁表——
   建库时间选在低峰期比较稳妥。
3. 保留期清理挂在每 24 小时一次的 `operations_cleanup` 上，不需要额外配置。

方案里的批次都做完了。后续想继续优化，建议按「先量后改」来：
先看 `operations` 的埋点找真正慢的接口，别再照着这份文档往下推。
