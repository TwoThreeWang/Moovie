# Moovie 新系统影视数据与播放架构实施方案

> 文档状态：实施设计稿  
> 适用项目：Moovie 影牛  
> 编写日期：2026-08-02  
> 目标版本：新系统分阶段演进版本  
> 实施原则：增量迁移、兼容旧数据、可观测、可回滚、不破坏现有播放器体验

## 1. 文档目的

本文档用于指导 Moovie 从当前“豆瓣元数据、资源网搜索、浏览器观看记录、在线用户记录相互独立”的结构，演进为以统一影视实体为核心的新系统。

实施完成后，系统应具备以下能力：

1. 搜索结果以“同一部影视”为单位聚合，不再将豆瓣资料和资源网结果割裂展示。
2. 未登录用户继续使用浏览器保存进度；登录后由服务端统一管理，首页和用户中心结果一致。
3. 豆瓣、TMDB、IMDb 等来源按字段互补，不因某次抓取数据不完整而覆盖已有优质数据。
4. 旧系统已有的 ArtPlayer、HLS、弹幕、自动续播和移动端优化得到完整保留。
5. 热门内容由豆瓣热门、TMDB 热门和站内真实热度共同产生。
6. 元数据和资源网数据拥有明确的刷新状态、退避策略和“当前无需更新”判断依据。
7. 冷门资源网数据可以安全降冷、压缩和清理，永久影视元数据不随资源删除。
8. 众包式播放成功率继续保留，并升级为可用于线路排序和自动切换的质量系统。
9. 同一影视的多个播放源可以按质量排序；发生故障时只切换到同一电影或同一剧集。

本文档描述目标架构、数据模型、接口、算法、迁移方式、测试方法和验收标准。具体页面视觉设计不在本文档范围内。

## 2. 当前系统现状与主要问题

### 2.1 当前三条核心链路

当前系统实际存在三套身份体系：

- 影视元数据：以 `movies.douban_id` 为唯一标识。
- 资源网数据：以 `vod_items.source_key + vod_id` 为唯一标识。
- 观看记录：主要以 `source + vod_id` 为唯一标识，并在浏览器和服务端各保存一份。

豆瓣、TMDB、资源网和观看记录之间主要依靠可空豆瓣 ID、标题、年份和前端参数临时连接，没有系统级的统一影视 ID。

### 2.2 当前问题的共同根因

九项需求并不是九个互相独立的功能问题，而是由两个根因产生：

1. 缺少统一影视实体。
2. 登录用户的观看进度没有唯一可信来源。

只在搜索页增加豆瓣卡片、在播放器上增加自动换源、或继续扩充 `vod_items` 字段，都无法彻底解决问题。新系统必须先建立稳定的领域模型。

### 2.3 已确认的具体风险

#### 元数据互相覆盖

当前豆瓣抓取和 TMDB 补充最终都会更新同一行 `movies`：

- TMDB 可以直接替换海报。
- 豆瓣强制刷新得到的结构化数据不一定包含 IMDb ID 和 TMDB 剧照。
- 当前 Upsert 会统一更新 `imdb_id`、`backdrops` 等字段，稀疏数据可能把已有补充字段清空。

因此，新系统不能继续采用“最后一次抓取覆盖整行”的方式。

#### 观看记录键不稳定

当前浏览器和服务端记录主要按 `source + vod_id` 区分。同一部影视切换资源站后，会产生另一条记录；同一剧集在不同源中的标签也可能不同。

#### 同步游标依赖客户端时间

当前使用浏览器 `lastSyncAt` 和客户端毫秒时间筛选增量数据。设备时间不准、离线后重新登录、删除记录、多个设备同时更新时，都可能出现漏同步或记录复活。

#### 成功率统计口径不一致

当前成功播放增加 `sample_count`，失败播放只增加 `failed_count`，读取时却使用 `(sample_count - failed_count) / sample_count`。这会造成成功率失真，极端情况下甚至出现负数。

#### 刷新与访问时间混用

资源网当前主要使用 `last_visited_at`，但“搜索发现、后台刷新、详情访问、真正播放”是不同信号。它们不能继续共用一个时间字段来决定刷新和清理。

## 3. 目标架构

```text
豆瓣原始数据 ─┐
              ├─> 元数据快照 ─> 字段级合并器 ─> media 统一影视实体
TMDB 原始数据 ─┤                                  │
IMDb / 外部ID ─┘                                  │
                                                  │
资源网 API ─> vod_items ─> 实体匹配器 ────────────┤
                                                  │
                                                  ▼
                                     media_units 电影/季/剧集单元
                                                  │
                                                  ▼
                              同一单元的候选线路、质量排序与故障切换
                                                  │
                                                  ▼
                                  ArtPlayer + 统一观看进度 + 质量事件
```

### 3.1 设计原则

1. **内部 ID 优先**：所有新业务关系使用系统内部 `media_id` 和 `media_unit_id`。
2. **外部 ID 只是映射**：豆瓣、TMDB、IMDb 都是外部标识，不再承担系统主键职责。
3. **原始数据与展示数据分离**：抓取结果先保存快照，再由确定性的合并器生成展示字段。
4. **元数据与播放资源分离**：元数据永久保存，资源允许过期、降冷和删除。
5. **电影与剧集统一建模**：播放器只接收一个明确的 `media_unit_id`，不自行猜测第几集。
6. **先兼容再切换**：新增表和字段、影子写入、回填、双读验证，最后才替换旧读路径。
7. **所有自动判断可解释**：实体匹配、热门融合、线路排序都保存评分组成和决策原因。
8. **所有生产清理可预演**：涉及删除时必须先 dry-run，展示目标、数量和引用关系。

## 4. 领域模型

### 4.1 统一影视实体 `media`

一条 `media` 表示一个用户可识别的影视目录实体。推荐允许父子层级：

- 电影：一条独立 `media`。
- 连续剧：系列为父 `media`，季可以是子 `media`。
- 豆瓣将每一季作为独立 subject 时，豆瓣 ID 绑定到季级 `media`。
- 综艺、动画按照实际季或系列结构处理。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 系统内部永久 ID |
| `parent_id` | `BIGINT NULL` | 系列与季的父子关系 |
| `kind` | `VARCHAR(20)` | `movie/series/season/show/animation` |
| `title` | `TEXT` | 最终中文展示标题 |
| `original_title` | `TEXT` | 原始标题 |
| `year` | `SMALLINT NULL` | 首映年份 |
| `season_number` | `INT NULL` | 季编号 |
| `release_date` | `DATE NULL` | 首映日期 |
| `status` | `VARCHAR(20)` | `announced/releasing/ended/unknown` |
| `summary` | `TEXT` | 最终简介 |
| `poster_url` | `TEXT` | 当前展示海报 |
| `backdrops` | `JSONB` | 规范化剧照列表 |
| `genres` | `JSONB` | 类型数组 |
| `countries` | `JSONB` | 国家地区数组 |
| `directors` | `JSONB` | 导演列表 |
| `actors` | `JSONB` | 演员列表 |
| `runtime_minutes` | `INT NULL` | 电影或单集时长 |
| `episode_count` | `INT NULL` | 已知集数 |
| `douban_rating` | `NUMERIC NULL` | 豆瓣评分，明确来源 |
| `tmdb_rating` | `NUMERIC NULL` | TMDB 评分，明确来源 |
| `field_provenance` | `JSONB` | 每个最终字段的来源和更新时间 |
| `metadata_hash` | `VARCHAR(64)` | 最终语义元数据哈希 |
| `completeness_score` | `SMALLINT` | 0–100 完整度 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 最终展示字段变更时间 |

说明：

- 豆瓣评分和 TMDB 评分不合并为一个含义模糊的 `rating`。
- `updated_at` 只在最终展示字段发生变化时更新，不因“检查后无变化”而更新。
- 现有 `movies.embedding` 可以在迁移期继续保留，最终迁移到以 `media_id` 关联的向量字段或独立表。

### 4.2 外部 ID `media_external_ids`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `media_id` | `BIGINT` | 关联 `media.id` |
| `provider` | `VARCHAR(20)` | `douban/tmdb/imdb` |
| `external_type` | `VARCHAR(20)` | `movie/tv/season/show` |
| `external_id` | `VARCHAR(64)` | 外部 ID |
| `match_method` | `VARCHAR(30)` | `exact/manual/automatic/imported` |
| `confidence` | `NUMERIC(5,4)` | 0–1 |
| `verified_at` | `TIMESTAMPTZ NULL` | 人工或规则确认时间 |

约束：

```text
UNIQUE(provider, external_type, external_id)
UNIQUE(media_id, provider, external_type)
```

TMDB 的 movie ID 和 tv ID 可能位于不同命名空间，因此唯一约束必须包含 `external_type`。

### 4.3 标题别名 `media_aliases`

用于搜索和资源匹配：

| 字段 | 说明 |
| --- | --- |
| `media_id` | 统一影视 ID |
| `alias` | 别名原文 |
| `normalized_alias` | 清洗后的匹配值 |
| `language` | 语言，可空 |
| `source` | 豆瓣、TMDB、资源或人工 |
| `alias_type` | 中文名、原名、又名、季标题等 |

索引：

- `normalized_alias` 的 `pg_trgm` GIN 索引。
- `(media_id, normalized_alias)` 唯一或去重索引。

### 4.4 元数据原始快照 `metadata_snapshots`

| 字段 | 说明 |
| --- | --- |
| `media_id` | 已关联的影视；匹配前允许为空 |
| `provider` | `douban/tmdb/wmdb` 等 |
| `external_type` | 外部媒体类型 |
| `external_id` | 外部 ID |
| `payload` | 原始 JSONB；网页解析结果也转换成规范 JSON |
| `content_hash` | 排除抓取时间等波动字段后的哈希 |
| `http_etag` | 可用时保存 |
| `http_last_modified` | 可用时保存 |
| `fetched_at` | 本次检查成功时间 |
| `changed_at` | 内容最近变化时间 |
| `unchanged_count` | 连续无变化次数 |
| `next_fetch_at` | 下次允许刷新时间 |
| `failure_count` | 连续失败次数 |
| `last_error` | 最近错误摘要 |

原始快照使系统可以在不重新访问外部站点的情况下重新运行合并规则。

### 4.5 资源网条目 `vod_items`

现有表保留并扩展：

| 新增或调整字段 | 说明 |
| --- | --- |
| `id BIGSERIAL` | 新增稳定内部主键 |
| `media_id BIGINT NULL` | 已匹配的影视实体 |
| `match_status` | `unmatched/automatic/verified/review/rejected` |
| `match_confidence` | 0–1 |
| `match_reason JSONB` | 评分明细和冲突信息 |
| `resource_status` | `active/cold/removed/broken` |
| `last_discovered_at` | 最近一次被资源站搜索返回 |
| `last_detail_checked_at` | 最近检查详情 |
| `last_changed_at` | 播放数据最近变化 |
| `last_played_at` | 最近实际播放 |
| `last_success_at` | 最近成功播放 |
| `next_refresh_at` | 下次允许刷新时间 |
| `content_hash` | 规范化详情哈希 |
| `unchanged_count` | 连续无变化次数 |

保留约束：

```text
UNIQUE(source_key, vod_id)
```

旧 `last_visited_at` 在迁移期保留，只用于兼容旧查询，不再作为清理的唯一依据。

### 4.6 播放线路 `vod_play_lines`

当前 `vod_play_url` 是一个包含多线路、多剧集的字符串，不适合跨资源站排序和故障切换。详情抓取后应解析为结构化表：

| 字段 | 说明 |
| --- | --- |
| `id` | 线路内部 ID |
| `vod_item_id` | 所属资源网条目 |
| `source_name` | 资源站返回的线路名称 |
| `source_order` | 原始顺序 |
| `format` | `hls/flv/mp4/unknown` |
| `status` | `active/broken/removed` |
| `content_hash` | 线路剧集列表哈希 |

### 4.7 播放单元 `media_units`

`media_units` 是观看进度和自动换源的真正主键。

| 字段 | 说明 |
| --- | --- |
| `id` | 播放单元 ID |
| `media_id` | 所属影视 |
| `unit_type` | `feature/episode/special/trailer` |
| `season_number` | 季编号，可空 |
| `episode_number` | 集编号，可空 |
| `absolute_number` | 动画等绝对集数，可空 |
| `title` | 单集标题 |
| `air_date` | 播出日期 |
| `runtime_minutes` | 单集时长 |

电影创建一个 `feature` 单元。剧集的每一集创建独立 `episode` 单元。

### 4.8 资源站剧集映射 `vod_episodes`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `play_line_id` | 所属播放线路 |
| `media_unit_id` | 映射后的统一播放单元，可空 |
| `source_episode_key` | 资源站原始剧集键 |
| `source_episode_title` | 原始标签，如“第03集” |
| `normalized_episode` | 规范化结果 |
| `play_url` | 当前播放 URL |
| `mapping_status` | `exact/automatic/review/unmatched` |
| `mapping_confidence` | 0–1 |
| `url_hash` | URL 变化检测 |

约束：

```text
UNIQUE(play_line_id, source_episode_key)
```

自动故障切换只能选择 `media_unit_id` 相同且映射置信度满足阈值的记录。

## 5. 元数据采集与合并

### 5.1 采集流程

```text
刷新任务到期
  -> 请求提供方
  -> 校验响应与外部 ID
  -> 规范化 payload
  -> 计算 content_hash
  -> 保存 metadata_snapshot
  -> 若 hash 变化，运行字段级合并器
  -> 若语义字段变化，更新 metadata_hash 并重新生成 embedding
  -> 计算 next_fetch_at
```

### 5.2 字段优先级

初始建议如下：

| 字段 | 第一来源 | 第二来源 | 说明 |
| --- | --- | --- | --- |
| 中文标题 | 豆瓣 | TMDB zh-CN | 保留别名 |
| 原始标题 | TMDB | 豆瓣 | 不覆盖更完整值 |
| 中文简介 | 豆瓣 | TMDB zh-CN | 空值不覆盖 |
| 导演/演员 | 豆瓣 | TMDB | 合并去重并保存来源 |
| 类型/地区 | 豆瓣 | TMDB | 规范化词表后合并 |
| 海报 | 人工固定 > 豆瓣/TMDB 质量评分 | 另一来源 | 不再固定由最后同步者覆盖 |
| 剧照 | TMDB | 豆瓣 | 去重、限制数量 |
| 上映日期 | TMDB | 豆瓣 | 精确日期优先 |
| 季集结构 | TMDB | 资源网推断 | TMDB 为主要结构来源 |
| 豆瓣评分 | 豆瓣 | 无 | 单独字段 |
| TMDB 评分 | TMDB | 无 | 单独字段 |
| IMDb ID | 豆瓣页面/TMDB 映射 | WMDB | 作为外部映射保存 |

### 5.3 合并规则

1. 空值不得覆盖已有非空值。
2. 抓取失败不得修改最终字段。
3. 提供方返回字段缺失，不等于该字段已被提供方删除。
4. 列表字段先规范化后去重，保留稳定顺序。
5. 人工固定字段优先级最高，自动同步不得覆盖。
6. 每个最终字段在 `field_provenance` 中保存：
   - 来源；
   - 外部快照 ID；
   - 选择时间；
   - 合并规则版本。
7. 合并器必须是确定性的：相同快照和相同规则版本应产生相同结果。

### 5.4 完整度评分

`completeness_score` 用于决定是否需要补充其他来源，不直接代表内容质量。

初始权重建议：

| 字段 | 分值 |
| --- | ---: |
| 标题 | 15 |
| 年份/日期 | 8 |
| 媒体类型 | 7 |
| 海报 | 10 |
| 简介 | 10 |
| 类型 | 8 |
| 国家地区 | 5 |
| 导演 | 8 |
| 演员 | 8 |
| 外部 ID 至少两个 | 8 |
| 片长 | 5 |
| 剧集结构或电影正片单元 | 8 |

满分 100。低于 70 的活跃影视优先进入补充队列。

### 5.5 向量更新

用于 embedding 的内容应来自最终合并后的稳定字段。生成前构造规范字符串并计算 `metadata_hash`：

```text
标题 | 原名 | 年份 | 类型 | 地区 | 导演 | 主演 | 简介
```

只有 `metadata_hash` 变化或向量为空时才重新生成 embedding。评分、剧照和热度变化不触发向量重建。

## 6. 影视实体匹配

### 6.1 匹配优先级

1. 资源网提供有效豆瓣 ID，且与标题/年份不存在严重冲突：精确匹配。
2. IMDb ID 或 TMDB ID 精确一致：精确匹配。
3. 标题、别名、年份、媒体类型、季数和演职员综合评分。
4. 无法达到自动阈值：进入待确认队列。
5. 存在明确冲突：标记 `rejected`，避免后台反复自动合并。

### 6.2 标题规范化

规范化过程至少包括：

- Unicode NFKC 规范化。
- 英文字母转小写。
- 全角半角统一。
- 清理分辨率、压制组、语言、修复版等资源标签。
- 识别但不丢弃“第 N 季”。
- 将“Season 2、S02、第二季”统一为季编号。
- 清理具体集数时必须保留季信息。
- 保存原始标题，任何清洗仅用于匹配。

### 6.3 自动评分

无外部 ID 精确命中时，初始权重建议：

| 特征 | 权重 |
| --- | ---: |
| 规范标题或别名相似度 | 0.40 |
| 年份一致或容差 | 0.15 |
| 媒体类型一致 | 0.10 |
| 季编号/剧集结构一致 | 0.15 |
| 导演/主演重合 | 0.10 |
| 原始标题或其他语言别名 | 0.10 |

阈值：

- `>= 0.88` 且无硬冲突：自动关联。
- `0.68–0.88`：进入人工复核。
- `< 0.68`：保持未匹配。

硬冲突包括：

- 年份差异过大且不是已知地区上映日期差异。
- 电影与电视剧类型冲突。
- 季编号明确不一致。
- 外部 ID 已绑定到另一个影视实体。

### 6.4 人工复核

后台应展示：

- 资源网原始标题、年份、演员、集数。
- 候选影视的豆瓣/TMDB 信息。
- 每项特征得分和冲突项。
- 确认关联、选择其他候选、新建影视、拒绝关联。

人工结果应保存为高优先级规则，后续刷新不得自动推翻。

### 6.5 回填策略

现有数据按以下顺序回填：

1. 将每条 `movies` 转换为一条 `media`，保存旧 ID 映射。
2. 写入豆瓣、IMDb 外部 ID。
3. 使用现有 `vod_douban_id` 精确关联 `vod_items`。
4. 对剩余记录运行标题/年份匹配，只影子记录结果，不立即影响用户页面。
5. 输出自动匹配率、待复核率和冲突率。
6. 抽样人工核对后再开启自动读取。

## 7. 搜索系统

### 7.1 搜索目标

搜索页应回答两个问题：

1. 用户搜索的是哪部影视？
2. 这部影视当前有哪些可播放资源？

不再把豆瓣资料作为独立卡片、把各资源站结果作为另一组平铺卡片。

### 7.2 新搜索流程

```text
用户输入关键词
  -> 规范化查询
  -> 搜索本地 media + aliases + external_ids
  -> 返回影视候选骨架
  -> 查询候选已关联的 active/cold 资源
  -> 本地元数据无结果时异步/限时查询豆瓣或 TMDB
  -> 资源不足时按候选规范标题并发搜索资源站
  -> 新资源落库并运行实体匹配
  -> 以 media 分组刷新结果
```

### 7.3 展示结构

每个影视结果包含：

- 最终海报、标题、原名、年份、类型和评分来源。
- 豆瓣/TMDB/IMDb 外部标识存在状态。
- 可用资源站数量。
- 当前最佳线路质量摘要。
- 电视剧当前可用集数和更新时间。
- “播放最佳线路”和“展开全部线路”。

未匹配的资源网结果可在页面底部放入“可能相关的其他资源”，不得伪装成已经确认的同一影视。

### 7.4 查询与缓存

- 搜索结果缓存键应包含规范化关键词、类型、年份和过滤参数。
- 影视候选缓存和资源网搜索缓存分开。
- 本地结果可立即返回；外部刷新通过 HTMX 局部更新。
- 同一关键词的外部抓取继续使用 `singleflight`。
- 缓存失效不能作为是否刷新元数据的唯一依据，刷新由 `next_fetch_at` 决定。

## 8. 观看记录与同步

### 8.1 权威来源

- 未登录用户：浏览器 `localStorage` 是唯一来源。
- 已登录用户：服务端是权威来源，浏览器是缓存和离线 outbox。
- 首页和用户中心必须使用同一份合并结果。

### 8.2 服务端模型 `playback_positions`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `user_id` | 用户 ID |
| `media_id` | 影视实体 |
| `media_unit_id` | 具体电影正片或剧集 |
| `position_seconds` | 播放位置 |
| `duration_seconds` | 客户端观测到的时长 |
| `progress_percent` | 服务端计算或校验后的百分比 |
| `completed` | 是否完成 |
| `last_vod_item_id` | 最近使用的资源 |
| `last_play_line_id` | 最近使用的线路 |
| `last_vod_episode_id` | 最近具体播放 URL 映射 |
| `activity_at` | 用户最后播放活动时间 |
| `server_version` | 服务端递增版本 |
| `deleted_at` | 删除 tombstone |
| `updated_at` | 服务端更新时间 |

约束：

```text
UNIQUE(user_id, media_unit_id)
```

“继续观看”列表按每个 `media_id` 取最近活动的未完成单元，因此同一电视剧不会因不同播放源出现多张重复卡片。

### 8.3 同步游标

服务端使用全局或分区单调递增序列作为 `server_version`：

```text
客户端携带 cursor=1200
服务端返回所有 server_version > 1200 的变更
响应 cursor=1288
```

不再使用浏览器时间作为增量查询边界。

### 8.4 客户端 outbox

每个浏览器生成持久化 `device_id`。本地操作保存：

- `operation_id`：UUID，用于幂等。
- `device_id`。
- `device_seq`：设备本地递增序列。
- `media_unit_id` 或可用于服务端解析的旧资源身份。
- `position_seconds`、`duration_seconds`。
- `occurred_at`。
- `operation_type`：`upsert/delete/complete`。

服务端对 `(device_id, operation_id)` 去重。

### 8.5 冲突规则

1. 不同 `media_unit_id` 不冲突。
2. 相同单元优先选择 `activity_at` 较新的操作。
3. 客户端时间最多允许领先服务端 5 分钟；超出时使用服务端接收时间。
4. 明确的删除操作生成 tombstone，不直接物理删除。
5. “重新观看并主动拖回前面”不能简单用最大播放秒数覆盖，应以新的播放会话活动时间为准。
6. 客户端基于旧版本提交时，服务端返回当前记录和冲突原因，客户端更新缓存。

### 8.6 登录时首次合并

登录后：

1. 浏览器上传旧 `moovie_play_state`。
2. 服务端优先通过豆瓣 ID 或 `source_key + vod_id + episode` 解析到 `media_unit_id`。
3. 无法解析的记录保留在 `legacy_payload`，不丢弃。
4. 服务端完成合并后返回统一记录和新 cursor。
5. 客户端写入 v2 本地结构，旧键保留一个迁移周期后删除。

### 8.7 删除同步

- 本地删除立即隐藏卡片并写入 outbox。
- 服务端设置 `deleted_at` 并提升 `server_version`。
- 其他设备同步后删除本地缓存。
- tombstone 建议保留 90 天。
- 超过 tombstone 保留期仍使用旧 cursor 的客户端必须执行一次全量同步。

### 8.8 建议接口

```http
POST /api/v2/history/sync
Content-Type: application/json
```

```json
{
  "device_id": "device-uuid",
  "cursor": 1200,
  "operations": [
    {
      "operation_id": "operation-uuid",
      "device_seq": 38,
      "type": "upsert",
      "media_unit_id": 90003,
      "position_seconds": 1260,
      "duration_seconds": 3600,
      "occurred_at": "2026-08-02T09:30:00Z",
      "last_vod_episode_id": 71008
    }
  ]
}
```

响应：

```json
{
  "cursor": 1288,
  "changes": [],
  "conflicts": [],
  "requires_full_sync": false
}
```

## 9. ArtPlayer 保留与适配

### 9.1 保留原则

播放器升级采用“外层适配、内核保留”，不重写现有播放器逻辑。

必须保留并建立回归用例的能力：

- ArtPlayer 基础配置和快捷键。
- HLS.js 自定义加载。
- FLV.js 自定义加载。
- iOS MSE 兼容和卡顿恢复。
- HLS manifest、fragment 和 media error 恢复。
- 动态缓冲区参数。
- 自动恢复上次播放位置。
- 自动播放下一集和倒计时取消。
- 弹幕加载、显示偏好、发送前服务端校验。
- 弹幕慢速默认值和关闭 heatmap。
- 画中画、AirPlay、全屏、网页全屏、旋转、锁屏、倍速。
- 播放进度本地保存和登录同步。
- 加载成功/失败质量上报。

### 9.2 依赖固定

生产环境不能继续依赖 `latest`：

- 固定 ArtPlayer 版本。
- 固定 `artplayer-plugin-danmuku` 版本。
- 固定 HLS.js 和 FLV.js 版本。
- 保存依赖文件或使用带完整性校验的固定 CDN URL。
- 每次依赖升级单独执行播放器回归测试。

### 9.3 新适配接口

播放器初始化只接受已经解析好的播放会话：

```javascript
initPlaybackSession({
  mediaId,
  mediaUnitId,
  candidateId,
  playUrl,
  title,
  episodeTitle,
  poster,
  resumePosition,
  nextUnit,
  danmakuContext
})
```

播放器通过回调上报：

```javascript
onManifestLoaded()
onFirstFrame(startupMs)
onPlayed10Seconds()
onProgress(position, duration)
onFatalError(errorCode)
onEnded()
onSourceSwitch(fromCandidate, toCandidate, reason)
```

播放器不负责：

- 判断两条资源是否是同一部影视。
- 猜测不同资源站的第三集是否相同。
- 自行查询整个资源列表。
- 自行计算最终线路排名。

### 9.4 现有播放器基线测试

在迁移前先为当前行为建立基线：

1. 首次播放无本地历史时不报错。
2. 有历史且剧集一致时恢复进度。
3. 历史剧集与当前剧集不一致时不错误跳转。
4. HLS 成功播放并上报一次成功。
5. 失败只上报一次当前尝试，但切换后的新尝试可以单独上报。
6. 视频结束触发正确下一集。
7. 弹幕服务失败不影响正片。
8. iOS Safari、桌面 Chrome 和移动 Chrome 真机或真实浏览器验证。

## 10. 众包播放质量系统

### 10.1 统计对象

统计维度必须至少达到：

```text
vod_item_id + play_line_id + media_unit_id
```

聚合到资源站级别的数据只用于站点健康度，不得代替具体线路和剧集质量。

### 10.2 播放尝试事件

建议事件：

| 事件 | 含义 |
| --- | --- |
| `attempt_started` | 开始尝试某候选线路 |
| `manifest_loaded` | manifest 或媒体头加载成功 |
| `first_frame` | 出现首帧，记录启动耗时 |
| `played_10s` | 连续有效播放至少 10 秒 |
| `rebuffer` | 播放中卡顿，可记录时长 |
| `fatal_error` | 无法恢复的播放错误 |
| `source_switched` | 自动或手动换源 |
| `ended` | 正常播放结束 |
| `abandoned` | 用户主动离开，不计作线路失败 |

质量统计中的“成功”初始定义为 `played_10s`，首帧仅用于启动速度。

### 10.3 防重复与防污染

- 每次播放尝试生成 `attempt_id`。
- 同一 `attempt_id + event_type` 幂等。
- 单个设备和 IP 哈希限流。
- 不保存原始 IP。
- 页面刷新可以产生新尝试，但短时间异常重复应折叠或降权。
- 管理员和自动探测流量单独标记，不混入真实用户指标。

### 10.4 聚合表 `playback_quality_rollups`

| 字段 | 说明 |
| --- | --- |
| `bucket` | 小时或天 |
| `vod_episode_id` | 具体候选 |
| `attempt_count` | 尝试数 |
| `success_count` | 播放 10 秒成功数 |
| `failure_count` | 明确故障数 |
| `first_frame_p50_ms` | 启动 P50 |
| `first_frame_p90_ms` | 启动 P90 |
| `rebuffer_count` | 卡顿次数 |
| `last_success_at` | 最近成功 |
| `last_failure_at` | 最近失败 |

原始事件建议保留 14–30 天，长期只保留汇总。

### 10.5 成功率置信度

不能仅用 `success / total` 排序。样本少的线路需要先验和平滑。

初始方案：

- 使用 Beta(2, 2) 先验，未知线路初始质量约为中性。
- 计算后验均值或 90% 置信下界。
- 最近 7 天权重大于历史数据。
- 连续失败额外施加短期惩罚。

这样可以避免只有一次成功的新线路直接排到大量稳定样本之前，也不会因一次偶发失败永久淘汰冷门线路。

## 11. 播放候选排序与自动故障切换

### 11.1 候选生成

请求播放某个 `media_unit_id` 时，服务端查询所有：

- 已匹配到同一 `media_id`；
- `vod_episodes.media_unit_id` 完全相同；
- 资源状态不是 `removed`；
- 线路状态不是长期故障；
- 未被版权或分类策略过滤；
- URL 当前存在；

的候选。

### 11.2 初始排序公式

建议将各项归一化到 0–1：

```text
candidate_score =
    0.55 * success_confidence
  + 0.25 * startup_speed_score
  + 0.10 * freshness_score
  + 0.10 * site_health_score
  - recent_failure_penalty
```

补充规则：

- 用户上次成功线路可获得轻微偏好，但不能压过明显故障。
- 没有样本的新线路以中性先验参与，不直接排末尾。
- 线路最近连续失败达到阈值后临时降级，而不是立即永久禁用。
- 排名结果保存组成分，后台可解释。

### 11.3 自动切换条件

以下情况可以触发自动换源：

- manifest 超时且重试耗尽。
- HLS 连续致命网络错误达到阈值。
- 无法恢复的媒体错误。
- 首帧等待超过配置阈值。
- 播放中连续长时间无法恢复。

以下情况不得自动判断为线路失败：

- 用户暂停。
- 用户主动离开页面。
- 浏览器自动播放策略阻止播放。
- 网络切换后短暂离线但尚未达到故障阈值。

### 11.4 同集安全约束

自动换源必须满足：

```text
next.media_unit_id == current.media_unit_id
AND next.mapping_confidence >= 0.90
```

如果没有满足条件的候选：

- 停止自动切换。
- 保留当前进度。
- 展示人工选择线路或重新搜索资源入口。
- 绝不能退回该资源站第一集。

### 11.5 切换流程

```text
检测当前线路致命故障
  -> 上报失败事件
  -> 保存 currentTime
  -> 服务端或本地候选集选择下一条
  -> 再次校验 media_unit_id
  -> ArtPlayer 切换 URL
  -> 新线路出现首帧
  -> seek 到原 currentTime
  -> 展示“已自动切换线路”提示
```

限制：

- 单次页面会话最多自动切换 2 次。
- 已失败候选写入本次会话排除集，防止循环。
- 切换失败后不得在候选间无限轮询。
- 自动切换过程仍然保留手动选源能力。

### 11.6 播放接口

```http
GET /api/v2/media-units/{unit_id}/playback-candidates
```

```json
{
  "media_id": 12345,
  "unit_id": 90003,
  "resume_position": 1260,
  "candidates": [
    {
      "candidate_id": 71008,
      "source_key": "source-a",
      "source_name": "线路1",
      "play_url": "https://example/video.m3u8",
      "score": 0.86,
      "quality_label": "稳定",
      "mapping_confidence": 1.0
    }
  ]
}
```

## 12. 热门好片融合

### 12.1 候选来源

- 豆瓣热门电影、电视剧、综艺和动画榜单。
- TMDB trending / popular。
- 站内系统热门。

所有候选必须先映射到 `media_id` 后再合并和去重。

### 12.2 系统热门信号

建议使用：

- 去重用户/匿名设备的有效播放数。
- 搜索结果点击播放数。
- 详情页进入播放的转化。
- 播放至少 10 秒的有效次数。
- 播放完成率。
- 想看、看过等站内互动。
- 资源是否有稳定可播放候选。
- 24 小时和 7 天时间衰减。

不能直接使用页面访问次数，避免爬虫和刷新污染。

### 12.3 排名融合

不同来源的原始分数量纲不同，使用加权 Reciprocal Rank Fusion：

```text
RRF(media) = Σ weight(source) / (60 + rank(source, media))
```

初始权重：

- 豆瓣：0.30
- TMDB：0.30
- 站内：0.40

附加规则：

- 没有任何可播放资源的影视可以出现在发现列表，但播放入口应明确显示“暂无资源”。
- 有资源但成功率极低时施加质量惩罚。
- 新上映影视可以获得有限的新鲜度提升，不能完全覆盖真实热度。
- 每类榜单独立融合，避免电影与电视剧互相挤占。

### 12.4 快照与缓存

建立 `popularity_snapshots`：

- 保存来源榜单、原始排名、映射结果、融合分和生成时间。
- 豆瓣/TMDB 榜单建议 3–12 小时更新。
- 站内热度建议每 15–60 分钟聚合。
- 前台使用已生成快照，不在用户请求中同步等待三个外部来源。

## 13. 更新调度

### 13.1 区分“检查”和“变化”

所有数据源都必须分别记录：

- 最近成功检查时间。
- 最近内容变化时间。
- 连续无变化次数。
- 下次检查时间。

检查成功但内容未变化时，只更新同步状态，不更新 `media.updated_at`。

### 13.2 元数据初始周期

| 状态 | 建议检查周期 |
| --- | ---: |
| 未上映、正在连载 | 6–24 小时 |
| 上映/完结后 90 天内 | 1–3 天 |
| 已完结且连续 3 次无变化 | 14–30 天 |
| 多年稳定电影 | 60–90 天 |
| 完整度低于 70 | 在限流下优先补充 |
| 用户或管理员强制刷新 | 立即入队 |

### 13.3 资源网初始周期

| 状态 | 建议检查周期 |
| --- | ---: |
| 正在连载且近期播放 | 1–6 小时 |
| 近期热门电影 | 1 天 |
| 稳定电影资源 | 7–30 天 |
| 最近播放失败 | 立即或短延迟刷新 |
| cold 资源 | 不主动刷新，访问时刷新 |
| removed 资源 | 搜索重新发现时恢复 |

资源站提供的 `vod_time` 只能作为提示，不能单独证明本地已经是最新数据。

### 13.4 内容哈希

计算哈希前需：

- 对 JSON 字段排序。
- 排除抓取时间、请求 ID 等无意义波动。
- 播放线路按稳定键排序。
- URL 可分别计算 `url_hash`，避免整个对象因参数顺序改变而误判。

### 13.5 失败退避

```text
1 次失败：15 分钟
2 次失败：1 小时
3 次失败：6 小时
持续失败：最多退避到 24 小时，并结合站点熔断
```

管理员强制刷新可以绕过 `next_fetch_at`，但不能绕过全局并发、超时和安全限制。

### 13.6 多实例任务租约

新系统如果运行多个应用实例，不能仅依赖进程内 goroutine。刷新任务应使用数据库租约：

- `status=pending/running/completed/failed`。
- `locked_by`、`locked_until`。
- `SELECT ... FOR UPDATE SKIP LOCKED` 领取任务。
- worker 崩溃后租约到期可重试。
- 相同 provider + external ID 保持幂等。

## 14. 冷数据管理与清理

### 14.1 数据分类

永久保留：

- `media`。
- `media_external_ids`。
- 元数据快照或至少最新有效快照。
- 人工匹配决策。
- 聚合后的播放质量数据。

允许降冷或清理：

- 过期播放 URL。
- 长期无人使用的资源网详情大字段。
- 已被资源站删除的线路和剧集映射。
- 到期的原始播放事件。
- 到期的搜索原始日志。

### 14.2 资源生命周期

```text
active
  -> 长期无播放且非近期发现 -> cold
  -> 资源站确认删除/长期故障 -> removed

cold
  -> 用户访问或搜索重新发现 -> active

removed
  -> 资源站重新返回 -> active
```

### 14.3 初始降冷条件

建议满足全部条件才进入 `cold`：

- 30 天无真实播放。
- 30 天无成功播放。
- 14 天未被资源站重新发现。
- 不是用户最近观看记录当前使用的唯一资源。
- 不是某影视唯一可用线路。

进入 cold 后可停止主动刷新，但先不物理删除。

### 14.4 物理清理条件

建议至少 60–90 天后才清理大字段，并满足：

- 已处于 `cold` 或 `removed`。
- 没有活跃观看会话引用。
- 不是唯一资源。
- 没有待处理人工匹配。
- 已保留可用于重新发现的 `source_key + vod_id + media_id` 最小记录。

### 14.5 Dry-run 要求

任何生产清理必须支持：

```text
cleanup resources --dry-run
cleanup resources --apply --batch-id=<dry-run批次>
```

Dry-run 输出：

- 候选总数。
- 按资源站分布。
- 按 active/cold/removed 分布。
- 被观看历史引用数量。
- 唯一播放资源数量。
- 将释放的大致存储空间。
- 示例记录。

Apply 必须引用一个未过期的 dry-run 批次，避免查询条件变化后直接删除不同数据。

### 15.3 v2 API 总览

v2 接口与现有 SSR/HTMX 路由并行存在，Handler 只负责鉴权、参数校验、调用领域服务和渲染，不直接实现匹配或排序规则。

| 方法与路径 | 责任 | 登录要求 |
| --- | --- | --- |
| `GET /api/v2/search` | 搜索统一影视和关联资源 | 否 |
| `GET /api/v2/media/{media_id}` | 获取合并后的影视资料 | 否 |
| `GET /api/v2/media/{media_id}/resources` | 获取分组后的资源摘要 | 否 |
| `GET /api/v2/media-units/{unit_id}/playback-candidates` | 获取同一播放单元候选 | 否 |
| `POST /api/v2/playback/events` | 幂等写入播放质量事件 | 否，登录信息可选 |
| `POST /api/v2/history/sync` | 推送本地操作并拉取服务端变更 | 是 |
| `GET /api/v2/history/continue` | 获取统一继续观看列表 | 是 |
| `POST /api/v2/media/{media_id}/refresh` | 管理员或受限强制刷新 | 是 |
| `GET /api/v2/admin/media-matches` | 获取待复核匹配 | 管理员 |
| `POST /api/v2/admin/media-matches/{id}/resolve` | 确认、拒绝或新建实体 | 管理员 |
| `POST /api/v2/admin/resource-cleanups/dry-run` | 生成清理预演批次 | 管理员 |
| `POST /api/v2/admin/resource-cleanups/{batch_id}/apply` | 应用已确认预演批次 | 管理员 |

播放事件示例：

```http
POST /api/v2/playback/events
Content-Type: application/json
```

```json
{
  "attempt_id": "attempt-uuid",
  "event_id": "event-uuid",
  "event_type": "first_frame",
  "media_unit_id": 90003,
  "candidate_id": 71008,
  "startup_ms": 1260,
  "position_seconds": 0,
  "occurred_at": "2026-08-02T09:30:00Z"
}
```

接口要求：

- `event_id` 全局幂等，重复提交返回成功但不重复计数。
- `candidate_id` 必须能够在服务端解析到提交的 `media_unit_id`。
- 匿名事件使用服务端签发或浏览器生成的随机设备 ID，不使用可追踪指纹。
- 所有列表接口设置明确的分页上限。
- 错误响应使用稳定错误码，例如 `unit_mismatch`、`candidate_unavailable`、`full_sync_required`。

### 15.4 后台管理最小范围

第一版后台不需要做成完整媒资管理系统，但必须支持：

- 查看统一影视、外部 ID 和字段来源。
- 查看某个最终字段为何选择豆瓣或 TMDB。
- 查看未匹配、低置信度和冲突资源。
- 手工绑定、拆分、拒绝匹配，并记录管理员与原因。
- 查看某集候选线路及评分组成。
- 查看刷新状态、最近错误并触发受限刷新。
- 查看清理 dry-run 批次并确认 apply。

人工操作必须写入审计表，至少包含操作者、操作前值、操作后值、原因和时间。

## 16. 分阶段实施计划

### 阶段 0：冻结基线与可观测性

目标：在重构前确认现有行为。

任务：

- 为搜索、历史同步、豆瓣抓取、TMDB 补充建立关键测试。
- 建立 ArtPlayer 浏览器回归清单。
- 记录当前搜索耗时、资源命中率、历史重复率、播放成功率。
- 修正当前成功率口径，但迁移时保留历史统计说明。
- 识别当前数据库规模和各表增长速度。

验收：

- 有可重复执行的基准和统计快照。
- 现有播放器在目标浏览器完成真实播放验证。

### 阶段 1：新增统一实体数据结构

目标：只加表和字段，不改变用户页面。

任务：

- 新增 `media`、外部 ID、别名、快照、播放单元等表。
- 为 `vod_items` 增加内部 ID 和匹配字段。
- 将现有 `movies` 回填到 `media`。
- 建立旧 `movies.id/douban_id` 到 `media_id` 映射。
- 所有新抓取开始影子写入元数据快照。

Feature flag：

```text
MEDIA_V2_SHADOW_WRITE=true
MEDIA_V2_READ=false
```

验收：

- 回填行数一致。
- 豆瓣 ID 唯一冲突为零或都有人工处理记录。
- 关闭 flag 后旧系统不受影响。

### 阶段 2：资源匹配与剧集结构化

目标：得到可靠的 `vod_item -> media -> media_unit` 关系。

任务：

- 精确回填现有 `vod_douban_id`。
- 实现标题规范化和匹配评分。
- 解析 `vod_play_url` 到线路和剧集表。
- 实现电影正片和剧集映射。
- 新增后台待复核页面。

Feature flag：

```text
RESOURCE_MATCH_SHADOW=true
RESOURCE_MATCH_AUTO_APPLY=false
```

验收：

- 精确 ID 关联准确率 100%。
- 自动匹配抽样准确率达到 99% 后才允许自动应用。
- 明确季数冲突不会自动合并。

### 阶段 3：统一搜索

目标：搜索按影视聚合资源。

任务：

- 实现 `UnifiedSearchService`。
- 新增 v2 搜索接口和 HTMX 片段。
- 旧搜索作为 unmatched 兜底。
- 展示资源数量和最佳线路。
- 对比旧、新搜索命中率和耗时。

Feature flag：

```text
UNIFIED_SEARCH_ENABLED=false
UNIFIED_SEARCH_PERCENT=0
```

发布：内部用户 → 5% → 25% → 100%。

验收：

- 同一影视多个资源站结果合并为一张卡片。
- 未匹配资源不会错误合并。
- 搜索 P95 不显著劣于当前系统。

### 阶段 4：统一观看记录

目标：首页和用户中心使用同一份记录。

任务：

- 新增 playback position 和同步版本。
- 实现客户端 outbox、device ID 和幂等操作。
- 实现登录首次迁移。
- 实现删除 tombstone。
- 首页和用户中心切换为统一查询。

Feature flag：

```text
HISTORY_V2_SHADOW_WRITE=true
HISTORY_V2_READ=false
```

验收：

- 同一集换源后只有一条继续观看记录。
- 两台设备可双向同步进度和删除。
- 离线记录登录后不会丢失。
- 关闭 v2 read 可立即回到旧展示。

### 阶段 5：元数据合并与刷新调度

目标：豆瓣/TMDB 真正互补，并可判断何时无需更新。

任务：

- 上线字段级合并器。
- 保存 provenance 和合并规则版本。
- 接入内容哈希、完整度、下次刷新时间。
- 将强制刷新改成任务队列。
- 仅在语义哈希变化时重建向量。

验收：

- 豆瓣刷新不会清空 TMDB 剧照或 IMDb ID。
- TMDB 刷新不会无条件覆盖人工/优质海报。
- 连续无变化的数据进入稳定退避。

### 阶段 6：质量统计与自动换源

目标：按真实质量排序并安全切换同集。

任务：

- 接入播放尝试事件。
- 建立质量汇总和候选评分。
- 播放器接入候选会话。
- 先上线排序，不开启自动切换。
- 观察一段时间后开启自动切换。

Feature flag：

```text
PLAYBACK_RANKING_ENABLED=false
AUTO_FAILOVER_ENABLED=false
```

验收：

- 成功率总在 0–100%。
- 线路统计区分不同剧集和内部播放源。
- 自动切换永远保持 `media_unit_id` 不变。
- 无同集候选时停止，不播放第一集。

### 阶段 7：热门融合与资源生命周期

目标：完成热门融合、降冷和安全清理。

任务：

- 接入 TMDB 榜单。
- 建立站内有效热度。
- 生成融合快照。
- 资源先进入 cold，不直接删除。
- 观察 30 天后运行首次 dry-run。
- 人工确认后分批 apply。

验收：

- 热门列表可解释三方来源。
- 元数据数量不会因资源清理下降。
- 清理前后活跃影视可播放率不下降。

## 17. 数据迁移与回滚

### 17.1 迁移原则

1. 所有 schema 变更优先 additive。
2. 旧列至少保留一个稳定发布周期。
3. 先影子写，再对账，再切读。
4. 大表分批更新，避免长事务和锁表。
5. 每批记录范围、成功数、失败数和耗时。

### 17.2 双写对账

重点对账指标：

- 旧 `movies` 与新 `media` 数量。
- 豆瓣 ID 映射唯一性。
- 旧资源网结果与新分组后的资源总数。
- 旧观看记录与新 position 的可迁移率。
- 同一用户重复影视数。
- 播放成功/失败事件总量。

### 17.3 回滚边界

- schema 和影子数据不必立即删除。
- 通过 feature flag 回退读路径。
- v2 写入必须保留足够字段，以便映射回旧 `source + vod_id` 播放链接。
- 自动换源出现异常时可独立关闭，不影响手动选源和播放器。
- 热门融合可以独立回退到豆瓣榜单。
- 清理 apply 不属于可通过 flag 回滚的操作，因此必须先 dry-run，并优先使用可恢复状态或软删除。

## 20. 安全与隐私

- 播放事件只保存必要的设备随机 ID，不保存浏览器指纹。
- IP 仅用于短期限流时哈希处理，不保存原值。
- 外部图片和 API 请求继续执行域名白名单、协议校验和 SSRF 防护。
- 播放 URL 如包含临时 token，日志和后台页面必须脱敏。
- history sync 必须校验记录属于当前登录用户。
- `media_id`、`unit_id` 等参数使用服务端关系校验，不能只信任客户端。
- 人工匹配后台需要管理员权限和审计记录。
- 清理 apply 需要管理员确认和批次 ID。

## 21. 验收标准

### 21.1 搜索与元数据

- 搜索同一影视时，豆瓣/TMDB 资料与多个资源网展示在同一个影视结果下。
- 精确外部 ID 匹配不存在一对多冲突。
- 元数据任一来源刷新不再清空另一来源有效字段。
- 搜索仍能展示未匹配资源，但明确标注未确认。

### 21.2 观看记录

- 未登录用户关闭浏览器后仍能恢复本地进度。
- 登录用户在首页和用户中心看到相同的继续观看列表。
- 同一集切换资源站后不产生重复卡片。
- 两台设备可同步更新、删除和完成状态。

### 21.3 播放器与换源

- 当前 ArtPlayer 功能清单全部通过回归测试。
- 候选默认按质量分排序。
- 自动换源保留当前播放进度。
- 电视剧第三集发生故障时，只能切换到确认的第三集。
- 无法确认同集时停止自动切换。

### 21.4 热门、刷新与清理

- 热门结果可以追溯到豆瓣、TMDB 和站内榜单贡献。
- 稳定元数据在连续无变化后自动降低刷新频率。
- 冷门资源先 cold，再经过 dry-run 和确认后清理。
- 资源清理不会删除 `media` 和外部 ID。

### 21.5 质量统计

- 成功率始终在 0–100%。
- 成功、失败和尝试数定义一致。
- 统计可以区分不同线路和剧集。
- 新线路不会因一个样本获得不合理的最高排名。

## 23. 上线前决策清单

以下事项在开始对应阶段前确认，不阻塞阶段 0 和阶段 1：

1. `media` 是否采用 `BIGINT`；本文推荐 `BIGINT`，便于现有 PostgreSQL/GORM 集成。
2. 系列与季是否都建立 media；本文推荐父系列 + 季级子实体。
3. TMDB 海报与豆瓣海报的默认质量选择规则。
4. 自动匹配后台的最小功能范围。
5. 原始 metadata snapshot 的保留周期；推荐永久保留最新有效快照，历史快照可按版本压缩。
6. 播放原始事件保留 14 天还是 30 天；本文初始建议 30 天。
7. v2 搜索灰度比例和内部测试用户范围。
8. 自动换源默认关闭还是小流量开启；本文推荐先只排序，观察后开启换源。

## 24. 最终实施结论

本次升级应以统一影视实体为第一优先级。搜索聚合、豆瓣/TMDB 互补、观看记录去重、热门融合、资源更新、冷数据清理和自动换源都依赖这层基础。

推荐的主线是：

```text
统一影视实体
  -> 资源与剧集映射
  -> 搜索聚合
  -> 观看记录统一
  -> 元数据合并与自适应刷新
  -> 质量排序和同集换源
  -> 热门融合与冷资源清理
```

整个过程不需要推倒现有系统。通过新增表、影子写入、批量回填、双读对账、feature flag 和分阶段切换，可以在保留旧 ArtPlayer 优化及现有业务能力的同时，逐步完成新系统架构。
