## 整体设计思路

系统采用**三层分离**架构，这是理解全部表的钥匙：

| 层 | 回答的问题 | 特点 |
| --- | --- | --- |
| **媒体身份层**（`media*`） | 这是哪一部作品？ | 干净、规范、唯一，与片源无关 |
| **资源层**（`vod_items` / `resource_*`） | 哪里能播？ | 脏数据，来自第三方采集站，随时失效 |
| **用户层**（`users` / `playback_*`） | 谁看了什么、看到哪了？ | 只引用媒体身份，不依赖具体片源 |

好处是：采集站换了、片源挂了，用户的观看记录和收藏不受影响，因为它们挂在 `media` 上而不是挂在某个站的链接上。

## 一、媒体身份层（「这部片子到底是哪一部」）

同一部片子在各采集站叫法五花八门（《肖申克的救赎》/《月黑高飞》/`The Shawshank Redemption`），这一层负责收敛成一个唯一身份。

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `media` | `id` | **核心主表**。一部作品一行：标题、原名、年份、海报、简介、类型、导演、演员、豆瓣/TMDB 评分、`embedding vector(768)`（向量检索）、`metadata_status`（元数据完整度） |
| `media_external_ids` | `id` | 外部 ID 映射表：`(provider, external_id) → media_id`，provider 为 `douban` / `tmdb` / `imdb` 等，带 `confidence` 和 `is_primary` |
| `media_aliases` | `id` | 别名与译名。`normalized_alias` 做了归一化（NFKC + 去标点空格 + 小写）并建了 `gin_trgm_ops` 索引，用于模糊匹配 |
| `media_units` | `id` | 拆到「集」的粒度：`unit_type`（feature/episode/special/trailer）、季号、集号、`episode_key`、播出日期、片长 |
| `media_source_snapshots` | `id` | 各数据源返回的原始 JSON 存档（`payload_json` + `payload_hash`），便于回溯与去重刷新 |
| `media_field_sources` | `(media_id, field_name)` | 字段级来源仲裁：记录「标题这个字段来自哪个 provider、优先级多少」，避免低优先级源覆盖高优先级数据 |

**要点**

- `media.douban_id` **不是必填**——以 TMDB/IMDb 为首个来源的记录同样是合法的规范媒体，唯一索引是部分索引（`WHERE douban_id <> ''`）。
- `media_units` 是连接「作品」和「具体某一集片源」的中间层。

## 二、资源层（「哪里能播」）

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `sites` | `id` | 采集站注册表：`key`、`base_url`、`enabled` 开关 |
| `vod_items` | `(source_key, vod_id)` | 从采集站抓回的**原始条目**，字段全部保留站方命名（`vod_name`、`vod_play_url`、`vod_remarks`…），另带质量统计 `avg_speed_ms` / `sample_count` / `failed_count` |
| `resource_media_links` | `(source_key, vod_id)` | **关键桥梁**：某站某条目 ↔ 哪个 `media`。含 `confidence`、`matched_by`（匹配依据）、`is_locked`（人工锁定后自动流程不再改动） |
| `resource_match_candidates` | `(source_key, vod_id, media_id)` | 自动匹配没把握时进入的**待审队列**，`status` 为 `review` / `verified` / `rejected`，`reason` 用 JSONB 存判据 |
| `resource_match_audits` | `id` | 人工审核流水：谁（`actor_user_id`）在何时把哪条改成了什么、改前状态是什么。只增不改 |
| `resource_play_lines` | `id` | 播放**线路**。同一条目常有多条线路（如「线路1 / 线路2」），`(source_key, vod_id, line_key)` 唯一 |
| `resource_episode_candidates` | `id` | 线路下每一集的**实际播放地址**：`play_url`、`format`、`quality`，并关联 `media_id` / `media_unit_id` |

**要点**

- 资源层数据天然不可靠，所以处处带 `resource_status`（active / cooled 等）和 `last_seen_at` / `last_accessed_at`，方便冷却和清理。
- 「线路 → 集」这个两级结构（`resource_play_lines` → `resource_episode_candidates`）在 0023 引入，取代了早期扁平的 `resource_episodes`。

## 三、播放与观看

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `playback_positions` | `id` | 观看进度：`position_seconds`、`duration_seconds`、`progress_percent`、`completed`。`server_version` 走独立序列 `playback_position_version_seq`，配合 `deleted_at` 做软删除，支撑多端同步 |
| `history_sync_events` | `version`（BIGSERIAL） | 多设备同步的**事件日志**。客户端按 `version` 游标增量拉取；`(user_id, device_id, operation_id)` 唯一保证幂等；`operation_type` 为 upsert / delete / complete，`conflict_reason` 记录冲突处理 |
| `playback_attempt_events` | `id` | 播放埋点明细：`attempt_started` / `manifest_loaded` / `first_frame` / `played_10s` / `rebuffer` / `fatal_error` / `source_switched` / `ended` / `abandoned`，`(attempt_id, event_type)` 唯一 |
| `playback_quality_rollups` | `(bucket, candidate_id)` | 上表按时间桶的**聚合结果**：尝试数、首帧成功数与总耗时、成功/失败/卡顿/切源计数，以及按失败原因分类（timeout / network / decode / http / unknown）。用来给线路和片源排优先级 |

**要点**：埋点明细写入频繁但查询少，聚合表才是选源决策的读取对象，这是典型的「明细 + rollup」拆分。

## 四、用户与社交

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `users` | `id` | 账号：`email`、`username`（均唯一）、`password_hash`、`role`、`douban_user_id`、`is_public`（是否公开主页）、`avatar`（默认 emoji 🎬） |
| `user_movies` | `id` | 个人片库：`status` 为 `wish`（想看）或 `watched`（看过），带 `rating` 和 `comment`。`(user_id, movie_id)` 唯一 |
| `comment_likes` | `id` | 短评点赞，`(user_movie_id, user_id)` 唯一防重复 |
| `comment_replies` | `id` | 短评回复，内容长度约束 1–300 字 |
| `danmakus` | `id` | 弹幕：`vod_key`、时间点、内容（1–50 字）、`mode`（0/1/2 滚动/顶部/底部）、`color`（`#RRGGBB` 正则校验）、`deleted` 软删除 |
| `monthly_reports` | `id` | 月度观影报告：观影数、总时长、均分、类型分布、年度最爱、连续天数、`persona_title` / `persona_line`（人设文案）、`percentile_rank`、`poster_wall` 海报墙。带 `status` 状态机（pending → generating → generated / failed） |
| `feedbacks` | `id` | 用户反馈：`type` 为 `bug` / `request` / `suggestion` / `dmca`，含管理员 `reply` 和 `status` |

## 六、榜单与生命周期

### 热门榜单

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `popularity_snapshot_runs` | `id` | 一次榜单构建任务：`media_type`（movie/tv/show/cartoon）、`status`（building → ready / failed）、`source_status` JSONB 记录各数据源成败、`expires_at` |
| `popularity_snapshots` | `(run_id, media_id)` | 榜单内容：`rank`、`rrf_score`（多源 RRF 融合分）、`final_score`、`source_ranks`、`playable_candidate_count`（有几个可播片源）、`quality_multiplier`、`freshness_boost` |

设计上是 **run 级整批切换**：新 run 构建完成并置为 `ready` 后才对外可见，避免用户看到半成品榜单。`(run_id, rank)` 唯一保证排名不重复。

### 资源清理

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `resource_lifecycle_batches` | `id` | 冷数据清理批次。`action` 目前仅 `cool`，`status` 为 `previewed` → `applied` / `expired`。预览阶段就算好 `candidate_count`、来源分布、`history_reference_count`（有多少被观看记录引用）、`sample_records` 抽样、`estimated_bytes` |
| `resource_lifecycle_batch_items` | `(batch_id, source_key, vod_id)` | 批次内的具体条目 + 变更前状态，可用于回滚 |

典型的**先预览、人工确认、再执行**两阶段设计，避免误删。

## 七、后台任务

| 表 | 主键 | 作用 |
| --- | --- | --- |
| `worker_jobs` | `id` | **统一任务队列**。`task_type` + `subject_key` 标识任务对象，`payload` JSONB 存参数，`priority` 排优先级，`attempt_count` / `max_attempts` 控制重试，`available_at` 支持延迟与退避，`locked_by` / `locked_until` 实现租约锁（防多 worker 抢占），`progress_total` / `progress_done` / `progress_failed` / `progress_cursor` 支持长任务断点续跑 |

0036 把原先分散的 `douban_sync_jobs` 和 `metadata_refresh_jobs` 合并进这一张表；0038 加了限流，0034 加了保留期清理。

## 核心数据流

```
采集站(sites)
    │  抓取
    ▼
vod_items ──── 匹配 ────► resource_match_candidates ──人工审核──► resource_match_audits
    │                              │
    │                              ▼
    └────────────────────► resource_media_links ─────────► media
                                                             │
                                                     media_external_ids
                                                     media_aliases
                                                     media_units
                                                             │
resource_play_lines                                          │
    └─► resource_episode_candidates ◄────────────────────────┘
                    │  用户点播
                    ▼
        playback_attempt_events ──聚合──► playback_quality_rollups
                    │                              │
                    ▼                              └──► 反馈优化选源顺序
        playback_positions ◄──同步──► history_sync_events ──► 多设备
```

一句话概括：**采集站抓 `vod_items` → 匹配到 `media` → 通过 `resource_media_links` 关联 → 用户播 `resource_episode_candidates` 里的地址 → 进度存 `playback_positions`，质量埋点回流优化选源。**
