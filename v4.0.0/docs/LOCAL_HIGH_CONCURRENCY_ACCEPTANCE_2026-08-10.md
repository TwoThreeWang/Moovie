# 本地高并发与资源稳定性验收（2026-08-10）

## 结论

新系统已通过本机进程级突发保护验收：在 200 并发下没有传输错误、健康检查失败、进程退出或端口重启；达到资源预算后会快速返回带过载标识的受控 503，不会继续无限创建请求、数据库连接或后台 goroutine。

这证明当前版本可进入 5% canary 的容量验证，不代表单实例可以承载任意数量在线用户，也不能替代生产容器的 OOM/restart 证据。热点详情页的本机测试已经触发默认重请求预算，灰度时应优先水平扩容和边缘限流，不能直接调大单实例并发。

## 验收环境

- 启动方式：本地直接 `go run ./cmd/web`，未使用 Docker 承载 Web。
- PostgreSQL：本地 Docker 中的 `moovie_v2`。
- Web：`PORT=5009`、`JOBS_IN_WEB=false`、`DB_AUTO_MIGRATE=false`。
- 运行时预算：`GOMAXPROCS=2`、`GOMEMLIMIT=700MiB`。
- 默认应用预算：总在途 64、重请求 12、图片 24、排队 100ms、数据库连接 12。
- 为隔离核心请求开销，本轮压测关闭成功访问日志；随后已增加 production 采样 10% 且最多 20 条/秒的双重日志预算，并通过单元测试。

- 另一轮 10,000 个详情请求洪峰期间同步探测 `/about` 100 次，轻量页面全部返回 200；重请求等待没有占满 64 个全局槽位。

热点详情页主动削峰比例较高是容量边界信号，不是错误消失。它说明保护机制生效，也说明在相同硬件和响应复杂度下，持续超过约 528 个成功详情请求/秒时需要增加 Web 副本、使用 CDN/页面缓存或降低入口速率。该数字是本机基线，不是生产 SLA。

## 本轮资源保护范围

- HTTP 总请求、重请求、图片代理分别使用固定并发预算，短队列超时后返回 503、`Retry-After: 1` 和 `X-Moovie-Overload`。
- 请求体、请求头、请求时间、TCP 连接数均有上限；`/health` 不访问数据库并绕过业务闸门。
- 搜索来源采用固定 worker 数；后台机会任务满载即丢弃可重试任务，不创建无限等待 goroutine。
- 出站连接按主机设上限；AppleCMS 响应限制 4MiB 并流式解码。
- 搜索缓存只保留渲染字段并限制 200 条；热门和 sitemap 冷缓存请求使用合并机制。
- 个性化推荐缓存限制为 512 个用户、TTL 一小时；同一用户冷缓存请求会合并，并丢弃评论、向量文本、剧照等非渲染大字段。
- Web 与 Worker 分离，分别限制内存、CPU、PID 和数据库连接；liveness 使用 `/health`，`/ready` 只用于摘流。
- 成功访问日志既采样又限制每秒数量；过载日志按秒聚合。

## 进入生产灰度前仍需完成

1. 从线上旧容器保存 `OOMKilled`、退出码、RestartCount、重启前日志和宿主机资源证据，确认现有重启的真实原因。
2. 在与生产相同 CPU、内存、反向代理、TLS 和数据库距离的 canary 环境重跑混合流量，不用本机数字直接推算生产容量。
3. 5% 灰度同时观察 RSS、CPU、重启数、数据库等待、文件描述符、P95/P99 和 `X-Moovie-Overload` 比例；正常时降载率目标低于 1%。
4. 持续降载超过 5% 时停止加流量并水平扩容；不要首先提高单实例的并发、连接或数据库池上限。
5. 保持现有功能开关和回滚边界；完成真实 iOS/Safari、播放故障、最终迁移与流量适配器验收后，才可扩大灰度。
