## 本地运行

本地功能验收使用直接 `go run`；Docker 镜像验证是另一个独立门禁。

### 1. 准备依赖

- Go `1.25.4`
- PostgreSQL `15+`
- `vector` 与 `pg_trgm` 扩展；migration 会尝试创建，数据库用户需要相应权限

TMDB、Ollama 和外部弹幕是可选增强，未配置时对应能力会关闭或降级，不影响基础页面启动。`.env.example` 中的 `CF_*` 变量目前只会被配置层解析，`cmd/web` 没有在当前装配流程中创建 Cloudflare AI Provider。

### 2. 创建数据库

`DB_NAME=moovie` 会被直接拒绝启动（防止误连旧库）。全新本地安装可以使用任意独立库名：

```bash
psql -h 127.0.0.1 -U postgres -c 'CREATE DATABASE moovie_new;'
```

先检查是否已存在，不要重复创建：

```bash
psql -h 127.0.0.1 -U postgres -l
```

### 3. 创建本地配置

```bash
cp .env.example .env
```

至少检查这几项：

```dotenv
APP_ENV=development
PORT=5008
SITE_URL=http://localhost:5008

DB_AUTO_MIGRATE=true
DB_HOST=localhost
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=请替换为本地密码
DB_NAME=moovie_new
DB_MAX_CONNS=12

# 单进程快速 smoke test 可填 true；Web + Worker 或 Compose 使用 false
JOBS_IN_WEB=false
APP_SECRET=请替换为足够长的随机值
```

应用会先读取 `.env`，再让当前进程中已导出的同名环境变量覆盖文件值。**不要使用 `source .env`**：`.env` 是应用配置文件，不保证每一行都符合 shell 语法。

### 4. 启动 Web

```bash
go run ./cmd/web
```

**注意 `JOBS_IN_WEB` 的取值**，这是最容易踩的坑：

- `JOBS_IN_WEB=true`：Web 进程自己启动唯一的任务 Dispatcher，单进程就够，适合本地快速验证。
- `JOBS_IN_WEB=false`：Web 不启动 Dispatcher，**必须另外启动 `cmd/worker`**；否则豆瓣同步、资料/短评/剧照/向量刷新、热门快照和运维任务不会被执行。请求内的资源站搜索和播放详情访问仍可工作，不要把"页面能打开"误认为 Worker 已经运行。

端口被占用时会看到 `bind: address already in use`。用 `lsof -nP -iTCP:5008 -sTCP:LISTEN` 查出占用进程，或改用 `PORT=5009 go run ./cmd/web`（换端口记得同步改 `SITE_URL`，否则分享链接和 sitemap 仍指向旧端口）。

默认访问 <http://localhost:5008>。另开一个终端检查：

```bash
curl http://127.0.0.1:5008/health
curl http://127.0.0.1:5008/ready
```

- `/health` 只检查 Web 进程是否存活，不访问数据库，适合作为容器 liveness。
- `/ready` 会检查 PostgreSQL，适合负载均衡判断实例是否可以接流量。

首次 migration 完成后，日常开发可以改为 `DB_AUTO_MIGRATE=false`，减少误用 schema 权限的风险。

### 5. 按需启动 Worker

需要验证豆瓣同步、资料刷新、向量、热门快照或运维告警时，在另一个终端运行：

```bash
JOBS_IN_WEB=false go run ./cmd/worker
```

只有 Web 侧 `JOBS_IN_WEB=false` 时才需要它。此时任务会保留为待处理状态，而不是由 Web 偷偷执行。

### 6. 停止服务

在各自终端按 `Ctrl+C`，Web 和 Worker 会收到 `SIGINT` 并进入优雅关闭。不要长期遗留多个不同端口的 `go run` 进程，否则浏览器可能访问到旧实例，造成"代码已改但页面没变"的假象。

## 配置如何生效

完整配置见 [`.env.example`](../.env.example)，主要分组：

| 分组 | 关键变量 | 作用 |
| --- | --- | --- |
| 应用 | `APP_ENV`、`PORT`、`SITE_URL`、`SITE_NAME`、`WEB_ROOT`、`APP_SECRET` | 运行环境、监听端口、模板目录和签名密钥 |
| 数据库 | `DB_AUTO_MIGRATE`、`DB_*` | 是否自动迁移、连接信息、时区 |
| HTTP 预算 | `HTTP_MAX_*`、`HTTP_QUEUE_TIMEOUT_MILLISECONDS` | 控制并发、排队、请求体和连接数 |
| 日志 | `HTTP_ACCESS_LOG_SAMPLE_PERCENT`、`HTTP_ACCESS_LOG_MAX_PER_SECOND` | 防止访问日志在流量高峰放大资源占用 |
| 搜索 | `SEARCH_*`、`OUTBOUND_MAX_CONNS_PER_HOST` | 上游超时、来源并发、缓存和熔断 |
| 热门快照 | `POPULARITY_REFRESH_MINUTES` | 控制快照重算周期 |
| 外部服务 | `TMDB_API_TOKEN`、`OLLAMA_*`、`DANMU_API_*`、`WIKIDATA_*` | 可选 Provider；`CF_*` 仅由配置层保留和解析 |
| 任务 | `JOBS_IN_WEB`、`WORKER_POLL_SECONDS`、`WORKER_CONCURRENCY` | 控制执行位置、扫描周期和全局并发槽数 |

生产环境额外强制校验：

- `SITE_URL` 必须使用 HTTPS。
- `APP_SECRET` 至少 32 字节且不能保留示例值。
- HTTP、搜索、数据库和外部连接参数不能超过代码中的安全上限。

配置加载失败时程序会在监听端口前退出。先看终端中的 `configuration failed` 及具体字段，不要只反复重启。

## 功能开关

统一搜索、历史 V2、播放候选排序、自动换源和热门快照均已固定启用，不再提供旧版切换开关。仍可调节的只有资源匹配策略：

1. `RESOURCE_MATCH_SHADOW=true` 时匹配候选只进影子表，不改动线上关联。
2. 观察影子表质量数据后，再决定是否开启 `RESOURCE_MATCH_AUTO_APPLY`。
3. `MEDIA_REVIEW_MATCH_THRESHOLD` 必须严格小于 `MEDIA_AUTO_MATCH_THRESHOLD`。

## 数据库 migration

结构变更由应用内嵌 SQL 完成（`internal/platform/database/migrations`，按文件名排序）。执行时会：

1. 打开一个数据库事务。
2. 获取 PostgreSQL advisory transaction lock，防止多个实例同时迁移。
3. 创建或读取 `schema_migrations`。
4. 跳过已经记录的版本。
5. 顺序执行剩余 SQL，并记录版本。
6. 全部成功后提交；任何一步失败都会回滚本次事务。

本地首次启动可以使用 `DB_AUTO_MIGRATE=true`。生产环境建议由受控发布步骤执行 migration（`cmd/dbmigrate`），Web 和 Worker 日常运行使用 `DB_AUTO_MIGRATE=false`。

新增变更请追加新文件，**不要修改已有的 migration 文件**——已执行过的版本不会重跑。

表结构详解见 [数据库表结构说明](数据库表结构说明.md)。

## 测试和验收工具

### 日常代码门禁

```bash
go build ./...
go vet ./...
go test -p 1 ./...
go test -race -p 1 ./...
```

各测试包共用测试库，必须串行运行（`-p 1`），避免互相清表。测试时不要让本地 Web 或 Worker 连接同一个测试库。

它们分别回答不同问题：

- `go build`：所有包和命令能否编译。
- `go vet`：是否存在常见的 Go 静态问题。
- `go test`：已有行为测试是否仍然通过。
- `go test -race`：并发测试过程中是否检测到数据竞争。

> **跑全量测试要加 `-p 1`**：各包共用同一个测试数据库、彼此会 TRUNCATE 掉对方的数据。本地同时在跑的 `go run ./cmd/web` / `cmd/worker` 同理，会互相干扰。

这些命令不能证明真实浏览器样式、外部 API、生产数据库或容器资源一定正常，因此不能跳过后续门禁。

页面 SEO 不由独立命令对比，而是由 `internal/content` 和 `internal/search` 的回归测试直接断言：`compat.Fetch` 抓取渲染后的页面，逐项检查 Title、H1、Description、Keywords、Robots、Canonical、OG/Twitter 标签和 JSON-LD。这些断言随 `go test -p 1 ./...` 一起运行。

### 专用工具

| 命令 | 作用 | 是否写数据 |
| --- | --- | --- |
| `cmd/burstcheck` | 验证突发请求、受控 503 和健康隔离 | 只发送读取请求 |
| `cmd/dbmigrate` | 应用目标库结构 migration | **是** |

```bash
go run ./cmd/burstcheck -h
go run ./cmd/dbmigrate -h
```

### 发布源码审计

[`scripts/release/source-audit.sh`](../scripts/release/source-audit.sh) 检查发布产物是否完整：`go.mod`、`go.sum`、`Dockerfile`、`docker-compose.yml`、`.dockerignore`、`web/templates` 和 migration 目录缺任意一个都会失败。它不构建镜像，也不修改 Git 或业务数据。

## Docker Compose

本地功能调试不依赖 Docker。需要验证最终容器时：

1. 将 `.env` 改为生产有效值，例如 HTTPS `SITE_URL` 和 32 字节以上的 `APP_SECRET`。
2. 将 `DB_HOST` 设置为 `postgres_default` 网络中可解析的 PostgreSQL 服务名，**不能写容器内部的 `localhost`**。
3. 确认外部 Docker 网络 `postgres_default` 已存在。
4. 按 Web 和 Worker 副本数核算数据库连接总和。
5. 先渲染配置，再构建和启动。

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

资源边界见 [并发与容量](并发与容量.md#容器资源边界)。

> `docker compose config` 通过只表示 YAML 和变量可以渲染，不代表镜像已构建、容器已健康或压测已通过。

### 使用 build.sh 更新服务器

服务器首次使用前需要确认：

1. 服务器能够通过 Git 拉取本仓库。
2. `.env` 已配置完成。
3. 外部网络 `postgres_default` 已存在。
4. 现有 WARP 容器已连接该网络，并能通过 `cloudflare-warp:1080` 提供 SOCKS5 代理；Worker 会使用它访问外部 HTTP 服务。

以后每次本地提交并推送后，在服务器执行：

```bash
./build.sh
```

脚本会执行 `git pull --ff-only`，然后重新构建并强制重建 Web、Worker，最后输出容器状态。服务默认映射到宿主机 `5008` 端口。

`build.sh` **不会**执行数据库 migration、备份、健康检查或流量切换。如果 Git 无法快进、缺少 `.env`、镜像构建失败或容器启动失败，脚本会立即停止。

## 上线和回滚

推荐发布顺序：

1. 冻结发布版本并记录提交号。
2. 以受控步骤执行 `cmd/dbmigrate`，确认 `schema_migrations` 已推进到目标版本。
3. 完成浏览器、播放、SEO、性能和高并发门禁。
4. 部署 Web 与 Worker，完成健康检查和写入 smoke test。

应用回退由部署平台负责，仓库不提供切流脚本。**不要通过删除数据库或逆向执行 schema migration 回退。**

## 生成文件约定

- 不要在项目根目录保存 `go build` 产生的可执行文件。
- 临时二进制统一输出到已忽略的 `bin/`：

```bash
go build -o ./bin/burstcheck ./cmd/burstcheck
```

- `.env`、日志、覆盖率文件和 `bin/` 不得进入 Git 或 Docker 上下文。
