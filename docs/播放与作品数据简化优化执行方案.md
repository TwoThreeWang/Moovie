# 播放与作品数据简化优化执行方案

日期：2026-09-11  
状态：方案已整理，尚未实施  
范围：作品展示、类型修正、资源采集过滤、规范选集、播放与换源、播放统计及相关数据迁移。

## 1. 目标与执行边界

本方案汇总本次会话已经确认的方向，并补充实现步骤和验收要求。文中的具体字段名、接口形状和迁移分批方式是执行建议，不代表这些细节已经在生产环境落地。

目标是减少重复数据和不同入口的规则分叉，缩短链路：

- 作品资料统一读 `media`，资源站资料在采集侧补齐规范资料。
- 内容单元统一存 `media_units`，电影版本不进入内容单元。
- 资源播放列表只在 `vod_items.vod_play_url` 保存一份过滤后的文本。
- 删除 `resource_play_lines`、`resource_episode_candidates` 两张持久化播放索引表。
- 后端实时解析资源，`/watch`、`/play` 共用过滤、选集、选源和页面数据逻辑。
- 资源级统计直接原子累计，取消按事件扫描重算速度的任务。
- 保留必要的内容可用性汇总、短期播放结果和用户历史；不为减少表数牺牲已经确认保留的功能。

本轮仅形成执行方案，不授权或执行生产删表、数据清理、发布。后续实施应保留工作区无关改动，并按阶段验证。

## 2. 触发问题与已核实事实

问题链接：`/watch/35811064?ep=720P&source_key=艾旦影视&vod_id=200749`。

会话中核实的线上 HTML 表明：

1. 原链接返回的页面没有播放器容器，初始化地址为空。
2. 页面实际使用直连播放数据，`entryPage` 为 `play`，虽然地址栏仍是 `/watch`。
3. 当前线路原始选集为“正片”，请求却保留 `ep=720P`。
4. 去掉 `ep` 后，页面返回播放器容器和非空 m3u8 地址；没有据此宣称视频实际起播成功。

本地提交 `0db886a` 将电影清晰度、语言版本合并为正片，增加了旧标签兼容，但入口、索引补建、直连选择之间没有统一规则。这是可确认的缺口；本次没有查询生产数据库，不能断言该作品具体迁移或索引状态。

其他已核对的当前行为：

- `mediaidentity` 类型归一会将综艺、动漫归为 `tv`，未知类型默认电影。
- 资源 Upsert 更新已有记录时未同步更新 `type_name`。
- 电影版本词表包含预告、花絮等，不符合新的内容过滤政策。
- `/watch` 选集目前从候选表分组，名称可能仍来自版本标签。
- 当前播放统计成功来自 `played_10s`，失败来自 `fatal_error`，速度来自 `first_frame`，事件口径不一致。
- 当前播放上报会改动 `vod_items.updated_at`，需要移除。
- `playback_attempt_events` 还服务热门榜、活跃作品刷新和运维指标，不只是速度统计。

## 3. 已确认的最终数据职责

| 数据结构 | 去留 | 最终职责 |
|---|---|---|
| `media` | 保留 | 作品身份、规范资料和四分类 |
| `media_units` | 保留、补充可用性字段 | 正片、季集、期次、播出信息，以及是否存在资源 |
| `resource_media_links` | 保留 | 已确认的资源与作品关联 |
| `vod_items` | 保留、调整统计字段 | 过滤后的原始格式播放列表、资源状态、资源级统计 |
| `resource_play_lines` | 删除 | 线路改为后端请求内解析结果 |
| `resource_episode_candidates` | 删除 | 地址候选改为后端请求内解析结果 |
| `media_field_sources` | 复用 | 字段来源和优先级，保护豆瓣及人工资料 |
| `playback_positions`、收藏数据 | 保留 | 用户进度、收藏和历史业务状态 |
| `playback_attempt_events` | 收缩 | 短期单次尝试结果、去重、热门计数；取消过程事件依赖 |

“四张核心表”仅指作品与播放资源核心，不表示全站只剩四张表。元数据来源、用户历史、收藏、任务和必要统计仍有各自用途。

历史迁移中的 `resource_episodes`、`resource_playback_health`、`playback_quality_rollups`、`resource_match_audits` 已有后续删除迁移，不能把早期建表文件当成生产现状。实施前核对实际 schema。

## 4. 作品资料与统一展示

### 4.1 记录级展示优先级

全站使用相同规则：

1. 找到对应 `media`：标题、海报、演员、导演、简介、年份等全部取 `media`。
2. 未找到对应 `media`：回退资源站资料。
3. 两者都不存在：历史、收藏可以使用已有快照作最后兜底。

有 `media` 但个别字段为空时，展示默认图或空状态，不在页面层混入资源站字段。通过采集侧补齐资料，解决暂时缺字段的问题。

历史位置、收藏时间、线路、版本、资源更新时间不是作品资料，不受此规则替代。

### 4.2 资源站临时补齐，豆瓣到达后覆盖

- 已确认豆瓣 ID 和资源归属，尚无作品记录：创建待完善的 `media`。
- 用资源站非空有效资料初始化，已有记录只补空缺字段。
- 豆瓣采集成功：按字段覆盖低优先级的资源站资料。
- 豆瓣字段为空：保留已有值，禁止空值覆盖。
- 后续资源站采集：不得覆盖豆瓣、TMDB 或人工已经提供的受保护字段。
- 人工修正继续优先；已有豆瓣与 TMDB 的字段级规则不因本次资源补齐而被全局推翻。
- 不凭未经确认的资源豆瓣 ID 或模糊片名将资料写入其他作品。
- 资源站内容完整，不等于豆瓣已成功采集；不能因此停止必要的豆瓣任务。

复用 `MergeSource` 与 `media_field_sources`，加入低优先级资源来源。资源站的“只补空缺”应明确实现，不能因为同优先级允许更新，就让多个站反复覆盖。

实现注意：当前 `seedExistingFieldSources` 会将无来源记录的已有字段视为豆瓣基线，新创建的资源站占位资料必须立即记录真实来源，不能被该兼容逻辑误标。当前刷新状态逻辑还会根据字段完整度标记 ready、更新时间和采集时间，需要区分“资料可展示”和“豆瓣抓取完成”。并发合并中字段值及来源记录应保持一致，避免低优先级结果晚到后覆盖高优先级结果。

写入前统一简介清理、演员导演结构、空值和海报格式；不把版本后缀、广告文案当成规范作品资料。

### 4.3 统一函数的范围

统一的是展示字段与记录选择规则，不是让每张卡片各查一次数据库。

- 复用现有播放视图组合逻辑，抽出共享的纯组合函数。
- 单页通过既有查询获取记录，列表页批量获取后调用同一规则。
- 核对搜索、首页、详情、播放、历史、收藏、片单、报告、用户主页、通知引用、分享元信息及相关 API 的资料输出。
- 同步更新缓存版本或清理受影响缓存，避免页面继续使用旧资源资料快照。

## 5. 分类与内容结构

### 5.1 四种展示分类

| 类型 | 展示 | 内容结构 |
|---|---|---|
| `movie` | 电影 | 一个正片 |
| `tv` | 剧集 | 按季、集 |
| `show` | 综艺 | 按季、期或稳定节目单元 |
| `cartoon` | 动漫 | 动画电影为正片，连续动画为分集 |

动漫电影与动漫剧集都显示为动漫，但单元结构不同。`media_type` 负责展示分类，`media_units.unit_type` 负责正片或分集。不能仅因不是 movie 就认定有多集，也不能凭暂时只有一个资源就认定是电影。

来源证据不足时允许暂时未确定，前端不新增第五个正式分类。未知值不再默认电影；旧查询、默认值和写入路径需要一起调整。

### 5.2 多站分类纠错

- 更新采集写入，确保已有资源的 `type_name` 也随有效新资料更新。
- 按资源站归一分类；动作、动画、纪录等歧义类别不能单凭题材决定正片结构。
- 只使用已确认关联的资源；按站点计证据，不让同站多条记录重复投票。
- 多站一致可补未知分类，冲突时不按最后一次抓取随意覆盖。
- 明确人工判断不能被自动纠错覆盖；同源转载也不能视作完全独立证据。
- 将纠错放在采集、关联或元数据更新后，不放在播放请求中。
- 具体分类映射和自动纠错阈值需用实际资源样本验证，不编造准确率。

电影与连续内容互改时核对旧单元及历史引用。不得直接删除被引用的单元，也不得让类型修正被下次元数据归一再次折回两类。

## 6. `media_units` 与选集可用性

### 6.1 保存规则

- 电影一个正片；720P、HD中字等版本不创建单元。
- 连续内容按稳定季集身份保存。
- 综艺日期、上下部分需要稳定区分，不能把第 5 期上、下覆盖成一行。
- 来源只有“第 3 集”而没有季信息时，不得仅凭标签把其他季映射过来；利用作品、资源身份中的季信息，无法确定时不自动跨来源合并。
- 元数据同步负责播出日期等信息；采集解析可以补缺失单元，不覆盖可靠播出信息。
- 多段电影仍对应一个正片单元，分段在解析结果中保留，不把“上、下”当互相替代的版本。

### 6.2 新增 `has_resource`

建议字段：`has_resource BOOLEAN NOT NULL DEFAULT FALSE`。

含义为：至少存在一个当前有效、过滤后受支持的地址；不代表已经网络探测成功。

更新触发：

- 采集新增、更新资源；
- 资源移除或失效状态变更；
- 资源站停用、重新启用；
- 资源关联作品发生变化；
- 类型或过滤规则变化、历史数据清理。

相关变化后，以作品为范围批量读取有效关联资源并解析，重新计算各单元状态。某个来源失去一集时，必须检查其他来源，不直接置 false。

并发更新要保证重算与资源变更的顺序一致，可复用数据库事务和按作品串行处理，不能让较旧的重算覆盖较新的状态。失败时保留可重试入口，不把数据库查询异常当成没有资源。

### 6.3 前端选集

- 规范列表取 `media_units`，有资源显示可点击按钮，无资源灰色不可点击。
- 播出日期与资源可用性分别展示，不能把资源采集时间当播出时间。
- 点击时后端再解析验证；已有页面与资源更新之间出现变化时返回明确不可用状态。
- 今日更新展示当天单元，继续播放仍回到用户历史单元，不强制跳到当天最新集。

## 7. 资源过滤与保存

`vod_play_url` 保存过滤后的资源站播放列表，保留原有分隔格式。

共享后端规则：

1. 解析线路和播放项。
2. 按版本、播放项标签及可靠备注过滤预告片、片花、花絮、彩蛋、TC。
3. 保留受支持的播放地址，延续当前格式支持范围；本次不顺带扩展 MP4 或网页解析。
4. 删除空线路。
5. 有有效项才作为可播放资源保存；TC 与 HD 并存只排除 TC。

不要对 URL 任意字符做“包含 TC”判断，也不要因为资源级备注存在 TC 就删除有明确 HD 标签的播放项。无标签或备注冲突需用实际样本制定有限规则，不能承诺识别未标注的低画质内容。

新增全禁用资源不保存、不返回搜索结果。已有资源变为全禁用时，清空可播内容或按既有移除机制处理，并重算可用性；不能跳过更新后继续使用旧地址。处理关联和用户引用，不用级联删除损失历史。

入口覆盖采集保存、详情刷新、即时搜索返回、TVBox 输出、播放页面、下载/复制链接及旧缓存。不能只过滤数据库写入却返回原始未过滤内存结果。

入库和读取共用同一解析过滤函数。后端读取时继续防御旧数据；前端不另写一套过滤逻辑。

## 8. 实时解析、播放与换源

### 8.1 内存结构的含义

后端 Go 读取 `vod_play_url` 后，临时构造线路、版本、地址及其内容单元映射。它们不落库，请求结束即可释放，不要求长期缓存。

删除两张表后，仍需知道“同一集有哪些地址”，所以保留临时候选对象。这不意味着让前端解析原始播放列表。

### 8.2 统一流程

```text
确认作品与资源范围
  → 批量读取资源
  → 后端解析过滤
  → 匹配规范内容单元
  → 选择资源、线路和版本
  → 输出统一播放器数据与来源列表
```

- `/watch` 为作品入口，使用关联资源。
- `/play` 为指定资源入口，没有规范作品也能直接播放。
- 共用解析、单元匹配、候选排序、地址选择、错误状态及主要模板，watch页面样式尽量不要改变。
- 删除播放请求中的反复写候选索引、重试查询和隐式切换另一套页面流程。
- `entry_page` 保持原入口语义；代码复用不改变历史继续播放的路由。

### 8.3 参数与标识

- 内容单元与版本参数分开，新链接不再把 720P 放入集身份。
- 有规范作品时优先传递单元身份；未关联资源保留来源内的精确标签匹配。
- 请求内候选标识应能区分资源、线路、版本、分段和地址，不依赖即将删除的数据库 ID，也不只依赖易变化的数组下标。
- 标识实现保持简单，可使用确定性组合或摘要；后端只接受当前解析集合内的选择，不信任客户端提交任意地址。
- 旧 `ep=720P` 等链接在已确认单正片场景兼容；连续内容匹配失败不得退回第一集。
- 明确请求的版本不存在时返回不可用或明确替代列表，不能静默播放错误内容。
- 自动换源只在同一内容单元内进行，排除本次失败地址并保持重试上限；多段内容不能错误切换到另一段。
- 无有效地址时展示空状态，不初始化不存在的播放器容器。

### 8.4 性能边界

单作品批量加载有效资源，只取所需字段；列表和首页避免逐卡、逐集查询。选集初始状态利用 `has_resource`，不为每个按钮重新解析全部资源。

实时解析性能需要测量资源条数、文本体积、数据库返回量和请求延迟。只有测量证明必要才增加缓存，并绑定播放列表内容版本及必要的关联/规则版本失效。不得为了“避免解析”重新构建一套复杂持久化候选系统。

## 9. 资源级速度与成功率

### 9.1 统计粒度和字段

同一条 `vod_items` 的所有线路、版本共享统计，接受它代表资源综合表现。

采用会话中认可的三个整数方案：

- `total_load_ms BIGINT`：确认成功样本的起播耗时总和。
- `success_count BIGINT`：成功样本数。
- `failure_count BIGINT`：失败样本数。

读取计算：

```text
平均耗时 = total_load_ms / success_count
成功率 = success_count / (success_count + failure_count)
```

零样本显示未测，不显示 0% 成功率。先转为适当精度计算，避免整数除法。统计总和代替反复舍入的平均值，成功写入只需加法。

### 9.2 单次结果定义

- 一次地址尝试生成唯一 `attempt_id`。
- 有效播放达到十秒确认起播成功，同时提交这次尝试此前测得的起播耗时。
- 成功前致命错误或超时确认失败。
- 主动离开、主动换源、自动播放被阻止不直接记资源失败。
- 成功后发生中途错误可以换源，但不再将同次尝试记失败。
- 新地址、新尝试重新计时并重置状态。

起播耗时使用一致的播放器事件定义，不把清单下载完成或整个十秒观察期当成起播时间。当前 `first_frame` 实际由 `canplay` 触发，实施时应选择并准确命名可验证的口径。

统计只能代表已上报的起播结果，不宣称完整播放成功率或真实用户数。校验资源身份、有效结果、耗时范围，保留既有限流，避免任意上报污染统计。

### 9.3 原子更新和时间字段

结果首次写入后，同一条 SQL 内累计资源计数；并发不先查询旧值再计算，重复结果不重复累计。

速度上报不得更新：

- `vod_items.updated_at`；
- `vod_time`、`last_seen_at`、`last_visited_at`；
- 内容 hash、内容版本等采集相关字段。

业务仍需最近播放、成功时间时，只改专用的 `last_played_at`、`last_success_at`，不用于内容更新时间展示。

累计值代表历史表现，不再称最近七天。播放地址集合实质变化时按明确策略重置统计，普通海报或标题更新不重置。旧版本页面的迟到结果需校验资源播放版本，不能污染新一轮累计。版本号或 fingerprint 的具体承载方式在实现时选择最小方案。

## 10. 播放结果表的收缩

`playback_attempt_events` 已存在，不是本次新增需求。用户“无需历史记录”原意位于累计统计说明，不等于删除用户历史与收藏。

采用短期结果方案，保留需要的去重和近七天热门能力：

- 一次尝试至多一个最终结果，`attempt_id` 唯一。
- 保存作品、可选内容单元、资源、成功/失败、成功起播耗时、播放版本和时间。
- 未关联作品的 `/play` 也能上报，作品与单元不能再强制非空。
- 删除候选 ID、线路表 ID 外键依赖。
- 结果插入与 `vod_items` 累计在同一 SQL/事务完成，冲突不累计。
- 不再记录清单加载、卡顿、结束等全部过程事件。
- 按明确期限清理，覆盖热门榜窗口和可接受重试期限；过期去重记录删除后，不声称无限期幂等。

可以改造原表或迁移为语义更准确的结果表；具体命名不是业务要求，避免长期新旧双表并存。

| 原功能 | 改造后 |
|---|---|
| 质量定时重算 | 删除任务与消费者，直接累计 |
| 近七天热门 | 按短期成功结果时间计数，不使用历史总次数替代 |
| 活跃作品资料刷新 | 使用最近成功结果或专用成功时间 |
| 运维成功、失败、耗时 | 按最终结果重新定义 |
| 卡顿、换源过程、开始到成功漏斗 | 没有过程事件后移除或明确不可用，不伪造零值 |
| 用户观看历史与收藏 | 继续保留原业务存储 |

成功结果不是独立观众计数。用户主动重试和多资源尝试可能贡献不同结果，榜单口径应如实说明。

## 11. 迁移与实施顺序

### 阶段 A：基线和依赖清单

1. 核对当前部署版本、实际表结构、约束、迁移状态和数据量。
2. 查全 SQL、Go 接口、模板、JS、Worker、脚本、测试及文档引用。
3. 记录问题影片、普通电影、多季剧、综艺、动漫、未关联资源等对照样本。
4. 记录旧请求数、耗时、可播判定和关键页面行为，供切换后比较。

完成条件：明确哪些消费者需要替换，不能仅搜索播放 Handler。

### 阶段 B：统一规则与增量 schema

1. 更新四分类归一和 `type_name` 同步；修复未知默认电影。
2. 加入资源站低优先级资料补齐，修正来源和采集状态语义。
3. 统一记录级作品展示函数，逐项接入页面和 API。
4. 建立共享过滤、解析、单元匹配逻辑。
5. 增加 `has_resource`、耗时总和及短期结果兼容结构。

完成条件：新逻辑可独立验证，旧部署仍可安全运行；此时不删表。

### 阶段 C：替换业务链路

1. 采集先过滤、保存、确认关联、补单元、重算可用性。
2. `/watch` 与 `/play` 切换到同一解析选择结果。
3. 替换手动、自动换源及接口的候选 ID 契约。
4. 切换搜索摘要、详情入口、今日更新和历史单元关联。
5. 接入单次结果原子累计，停止旧质量任务写同一统计字段。
6. 替换热门榜、活跃刷新、运维指标和清理任务。

完成条件：正常业务不再读写两张索引表；旧客户端请求有明确兼容或拒绝行为。

### 阶段 D：数据回填与切换验证

1. 分批清理历史播放列表，更新受影响可用性。
2. 修复电影错误版本单元；先迁移历史等引用，再处理重复或废弃单元。
3. 复核跨季、综艺、动漫，不能批量把所有旧单元合并成正片。
4. 按新单次结果口径迁移短期事件，明确“成功后失败”等冲突的裁定。
5. 原有平均耗时与成功计数来自不同事件集合，不能直接乘起来伪造精确总耗时。根据可重建的明细回填一致样本；无法重建的资源保持未测或明确重置。
6. 为新旧统计和重试去重制定单一切换时点，禁止同一结果由旧任务和新 SQL 双重计入。
7. 清理或升级作品资料、播放摘要、页面与脚本缓存，兼容仍打开的旧页面。

完成条件：迁移可重入，有处理数量、冲突和失败清单，关键行为与性能已核验。

### 阶段 E：删除旧结构与收尾

1. 停止旧代码和 Worker，确认没有活动消费者。
2. 删除候选/线路相关外键、索引、接口字段和无用任务。
3. 删除 `resource_episode_candidates`、`resource_play_lines`。
4. 完成结果表收缩，清理不再使用的过程事件逻辑。
5. 更新数据库结构、业务流程、架构说明和发布说明。

禁止直接 `DROP ... CASCADE` 让数据库替代依赖审计。生产删除前按实际环境完成备份与恢复验证。新旧 schema 不兼容后，不能只回滚代码；需保留对应恢复路径。

## 12. 验收清单

### 作品与分类

- 已确认豆瓣 ID、尚未采集：规范记录可由资源站补齐，全站资料一致。
- 豆瓣到达后有效字段覆盖，空字段保留；后续资源站不能覆盖回去。
- 人工与其他已确认字段来源不被错误降级。
- 资源站资料齐全仍能触发必要豆瓣采集。
- 多站冲突、未知分类不会默认电影；动漫电影和连续动漫结构正确。
- 记录级回退覆盖历史、收藏与其他作品展示；列表没有新增逐条查询。

### 内容与资源

- 电影多个版本只对应一个正片，版本不进入选集。
- 普通剧、多季同集号、综艺日期和上下期不合并错。
- 预告、花絮、彩蛋、TC 全过滤；TC/HD 混合只剩允许项。
- 新全禁用资源不入库不展示；旧资源变全禁用不会残留可播状态。
- URL 恰好包含 tc 字符不会被误杀。
- 去掉一个来源仍有其他来源时 `has_resource` 保持 true；最后一个来源移除时变 false。
- 元数据已知但资源未更新的单元灰色不可点。

### 播放与历史

- 原问题链接和历史版本标签可兼容到正确电影正片。
- 第 3 集无资源时不退第一集，换源保持同一单元和分段。
- 未关联 `/play` 可以播放和上报。
- 请求具体版本失效时结果明确，不静默跳错。
- 空地址页面不调用播放器初始化。
- `/watch`、`/play` 历史入口及进度保持正确，今日更新不改变继续播放目标。

### 统计与性能

- 成功后报错不会给同一次起播同时计成功失败。
- 同一尝试重复请求只累计一次；并发结果不丢计数。
- 新换源独立计时，平均值样本与成功计数一致。
- 零样本、异常耗时、无效资源和迟到旧版本结果处理正确。
- 上报前后资源 `updated_at`、采集时间和内容版本不变。
- 最近七天热门仍按时间窗口统计；运维没有继续展示失去数据基础的指标。
- 批量选集、首页与搜索无 N+1 查询；比较改造前后延迟、数据库返回量及解析成本。
- 运行受影响模块测试、构建及契约检查；使用实际渲染页面和浏览器验证关键路径。
- 本地测试、浏览器验证、生产数据核验和真实视频起播分别报告，不相互替代。

## 14. 本方案保留的实际限制

- 多站分类没有经过准确率抽样，不能承诺自动纠错完全正确。
- `has_resource` 是存在性汇总，不是实时连通性保证；资源变更后必须可靠重算。
- 实时解析免去候选同步，但仍需内容匹配，不能消除不规范上游标签带来的全部歧义。
- 资源级统计无法区分同资源各地址的好坏，累计统计不代表近期状态或完整播放成功率。
- 短期去重不是永久去重，不再保存过程事件就不能保留原有全部过程指标。
- 生产 schema、实际数据质量、容量和部署兼容性尚待执行阶段核验。

执行完成的标准是：保留功能有验证，废弃消费者已移除，旧数据有迁移记录，生产链路不再依赖两张播放索引表，而不只是删表 SQL 已执行。

## 本地执行记录（2026-09-12）

已实现的结构与行为：

- 共享 `playurl` 过滤与内容身份解析，`mediaunits` 维护单元可用性；播放页读取不再补写候选索引。
- 两个播放入口共用页面、选集和选源，保留剧集、期号、电影版本及分段；缺失单元禁用，明确指定失效来源时不会静默播放其他内容。
- `mediaview` 统一记录级资料优先；搜索批量加载规范资料。资源仅补齐低优先级空字段，豆瓣采集独立排队；豆瓣/TMDB 采集不再先整条覆盖受保护字段。
- 新增 `playback_results`，attempt_id 去重、资源版本校验与原子累计；删除旧质量 Worker 和过程事件消费者。平均加载耗时为 canplay，成功定义为有效播放满 10 秒。
- 0063 / 0064 / 0065 与 `cmd/playbackreconcile` 提供结构切换、旧列表清洗、单元重算及可确认的电影历史引用修复；测试数据库必须显式使用 `moovie_test_` 前缀，避免误清本地业务数据。
- 回填改为服务继续运行时执行：0065 只加常量默认值的进度列；`playbackreconcile` 按 `resources`、`units`、`history` 分阶段串行处理，单条事务带锁等待与超时并 `SKIP LOCKED`，繁忙记录留到下轮；进度记在行上，限量、到时和停止信号都按已提交批次收尾。`history` 阶段会删除旧版本单元，必须显式 `-maintenance` 并停止进度写入，不随在线回填执行。
- 发布步骤已写入《开发与发布》，数据库、架构和业务流程文档同步更新。

验证使用独立 PostgreSQL 测试库，未改动生产数据库。核心模块回归、完整构建、静态检查已通过；全仓回归的失败与限制见本次交付说明。浏览器使用实际 player.js 和模拟 Artplayer 验证 10 秒成功阈值、失败去重、重新尝试、单元/分段链接和空地址保护；它不证明真实 HLS 解码、移动端真实设备或第三方资源站网络可用。

解析器微基准：1000 条、约 37 KB 播放列表，三次测量约 2.40–2.52 ms/op。此数值只说明本地解析成本，不是生产请求延迟，也没有据此声称端到端性能提升。

生产备份恢复演练、维护窗口迁移、全量回填、真实片源/设备验收与上线后的指标观察尚未执行，不能把本地代码完成等同于生产切换完成。
