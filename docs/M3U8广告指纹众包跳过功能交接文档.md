## 1. 目标

在 Moovie 的 `/play` 和 `/watch` 点播页面中，对 M3U8 内插入的重复广告片段进行众包识别：

1. 前端只分析 M3U8 文本，不下载广告 TS 来计算指纹。
2. 未达到共识的疑似广告正常播放，并显示不影响观看的确认提示。
3. 用户确认后立即跳过该候选片段的剩余部分，并异步提交确认票。
4. 达到保守共识阈值的广告，在后续播放中于媒体分片加载前识别并跳过，尽量不请求广告分片。
5. 广告指纹全局复用，不按资源网、电影、电视剧、集数或出现时间分别存储。
6. 功能只对主动开启的登录用户生效；设置保存到用户表，全端通用。
7. 所有识别或后端异常必须失败开放：最多漏跳广告，绝不能阻塞正常播放。

## 2. 已确认的产品决策

以下内容已经确认，实施时不要重新改成其他方案。

### 2.1 广告指纹全局复用

- 匹配键只有广告片段指纹。
- 不存储 `source_key`、资源网、电影 ID、集数、M3U8 URL、广告开始时间、广告结束时间或广告时长。
- 相同广告片段出现在不同影视、不同集数或同一个 M3U8 的多个位置时，应匹配同一条指纹记录。
- 广告时长和当前出现区间由本次 M3U8 实时计算，不进入数据库。

### 2.2 后端不代理和重写 M3U8

- 后端不抓取第三方 M3U8。
- 后端不代理 TS、密钥或其他媒体资源。
- 后端不返回重写后的播放清单。
- 前端继续直接使用原播放地址，通过 hls.js 的播放清单加载器读取并在内存中处理 M3U8 文本。
- 这样避免额外网络跳转、URL 重写、相对路径、鉴权参数、CORS 和 SSRF 问题。

### 2.3 保守自动跳过

不能因为一次确认或者仅仅 `confirm_count > reject_count` 就自动跳过。自动跳过必须同时满足：

```text
当前片段通过结构检测
AND 指纹精确匹配
AND confirm_count >= 5
AND confirm_count / (confirm_count + reject_count) >= 0.80
AND 0 < 当前候选时长 <= 120 秒
AND 当前候选不是播放清单的主体部分
```

确认比例达到 80% 已经隐含 `confirm_count > reject_count`。

阈值作为后端和前端共享语义的代码常量，不增加配置中心、后台设置或数据库状态字段。首版常量：

```text
MIN_CONFIRM_COUNT = 5
MIN_CONFIRM_RATIO = 0.80
MIN_REJECT_COUNT  = 3
MAX_AUTO_SKIP_SECONDS = 120
MATCH_TIMEOUT_MS = 250
MAX_MATCH_FINGERPRINTS = 20
```

状态计算：

| 状态 | 判定 | 播放行为 |
|---|---|---|
| `unknown` | 数据库无记录 | 结构高度疑似时询问 |
| `pending` | 有记录但未达到正向或负向门槛 | 结构高度疑似时询问 |
| `confirmed` | 确认数至少 5 且确认比例至少 80% | 满足所有结构保护后自动跳过 |
| `rejected` | 否认数至少 5 且否认数大于确认数 | 正常播放，不再提示 |

例子：

| 确认 | 否认 | 状态 |
|---:|---:|---|
| 1 | 0 | `pending` |
| 4 | 0 | `pending` |
| 5 | 0 | `confirmed` |
| 5 | 1 | `confirmed`，确认比例约 83% |
| 5 | 2 | `pending`，确认比例约 71% |
| 20 | 5 | `confirmed`，确认比例 80% |
| 3 | 5 | `rejected` |

数据库保存的是确认次数和否认次数，不是独立用户数。当前方案明确不保存用户与指纹的投票关系，因此不能宣称“5 个独立用户确认”。

### 2.4 用户设置保存到用户表

- 用户表增加 `ad_skip_enabled boolean NOT NULL DEFAULT false`。
- 登录用户默认关闭，需要主动开启。
- 未登录用户固定关闭。
- 设置以数据库为唯一真相来源，不用 `localStorage` 保存开关。
- 在一个设备开启后，其他设备下一次请求页面时读取同一设置。
- 不做 WebSocket、轮询或跨设备实时推送。

### 2.5 开关直接服务端渲染

当前全局 `identity.LoadUser` 已经在每个普通页面请求中读取完整用户记录并放入 `gin.Context` 的 `user_info`。因此：

- `/play` 和 `/watch` 初始化播放器时，直接传入 `adSkipEnabled: true/false`。
- 播放页开关直接根据 `.UserInfo.AdSkipEnabled` 渲染。
- 不为了广告设置增加播放页额外查询。

这能同时保证首段广告识别在媒体加载前生效，并且开关 UI 不阻塞或延迟播放器。

## 5. 数据库设计

### 5.1 迁移

建议迁移文件：

```text
internal/platform/database/migrations/0054_ad_skip.sql
```

内容语义：

```sql
ALTER TABLE users
    ADD COLUMN ad_skip_enabled boolean NOT NULL DEFAULT false;

CREATE TABLE ad_fingerprints (
    fingerprint bytea PRIMARY KEY,
    confirm_count integer NOT NULL DEFAULT 0 CHECK (confirm_count >= 0),
    reject_count integer NOT NULL DEFAULT 0 CHECK (reject_count >= 0),
    CHECK (octet_length(fingerprint) = 32)
);
```

不要增加以下字段：

- `source_key`
- `movie_id`
- `media_id`
- `episode`
- `start_time` / `end_time` / `duration`
- `status`
- `created_at` / `updated_at` / `last_seen_at`
- 独立投票明细表

`status` 由两个计数实时派生。播放只按当前候选指纹精确查询，不做全表扫描，因此表增长不会造成前端负担。

### 5.2 原子投票

确认和否认都使用单条 `INSERT ... ON CONFLICT DO UPDATE` 原子累加，不能执行“先查询、再更新”。

确认语义：

```sql
INSERT INTO ad_fingerprints (fingerprint, confirm_count, reject_count)
VALUES ($1, 1, 0)
ON CONFLICT (fingerprint) DO UPDATE
SET confirm_count = ad_fingerprints.confirm_count + 1
RETURNING fingerprint, confirm_count, reject_count;
```

否认同理累加 `reject_count`。

## 6. 广告指纹定义

### 6.1 首版是播放清单指纹，不是感知内容指纹

为了不加载 TS，首版不能对视频画面或音频做感知哈希。它计算的是候选块在 M3U8 中的稳定签名。

这意味着：

- 同一组广告分片以相同路径和时长序列出现在不同影视中，可以匹配。
- CDN 域名或临时查询参数变化不应影响匹配。
- 如果相同广告被重新切片、重新编码、重新命名或使用完全不同路径，会得到新指纹，需要重新众包确认。
- 不要为了跨编码匹配而下载 TS；这不属于首版范围。

### 6.2 规范化输入

对一个候选块中的每个媒体分片，按顺序生成：

```text
round(extinf_seconds * 1000) + "|" + normalized_uri_path + "|" + optional_byterange
```

然后用换行拼接所有分片，使用浏览器原生 Web Crypto：

```text
SHA-256(TextEncoder(canonical_block_text))
```

最终发送 64 字符小写十六进制字符串；后端严格解码为 32 字节 `bytea`。

URI 规范化规则：

1. 以当前媒体播放清单 URL 为基准解析相对地址。
2. 只保留 URL pathname。
3. 去掉 scheme、host、port、query 和 fragment。
4. 保留完整 pathname，不能只保留通用的 `0001.ts` 文件名，否则容易碰撞。
5. 不把密钥 URI 写入指纹；密钥变化只作为结构候选信号。密钥轮换不应让同一组媒体分片失配。

指纹只对结构候选计算，通常每个播放清单 0～3 个，不对整部影片的每一个滑动窗口暴力计算。Web Crypto 对这点文本计算 SHA-256 不会形成可感知的播放开销。

## 7. M3U8 候选检测规则

### 7.1 适用范围

- 只处理 VOD HLS 媒体播放清单。
- 播放清单必须包含 `#EXTINF`。
- 优先要求 `#EXT-X-ENDLIST`；直播、IPTV 和持续刷新的事件流关闭该功能。
- `/iptv`、`/player` 手动播放器和原生 HLS 降级路径首版不启用。
- 主播放清单本身不计算候选；等 hls.js 请求到具体 level 媒体播放清单后再处理。

### 7.2 分块边界

按以下边界切分连续媒体分片：

- 播放清单开始和结束。
- `#EXT-X-DISCONTINUITY`。
- `#EXT-X-KEY` 的 URI 或 METHOD 变化。
- 连续分片 URI 的父目录族明显变化。

不能因为单独一个边界就判定广告。

### 7.3 主体基线

以累计时长最长、分片数量明显占主导的连续块作为正片主体基线。主体块永远不能作为自动跳过候选。

如果无法可靠找出主体基线，整条播放清单失败开放，不提示、不跳过。

### 7.4 高度疑似条件

候选首先必须满足：

- 总时长在 5～120 秒之间。
- 至少包含 2 个媒体分片。
- 不是累计时长最长的主体块。
- 不占播放清单总时长的主要部分。

然后从以下信号中至少满足 3 项：

1. 位于播放清单开头或结尾。
2. 被 discontinuity 边界包围或与主体之间存在 discontinuity。
3. 分片 URI 目录族与主体不同。
4. 密钥 URI 或 METHOD 与主体不同。
5. 分片时长模式与主体明显不同，例如广告约 3 秒一片而正片约 10 秒一片。
6. 相同规范化候选块在同一播放清单的其他位置重复出现。

重复出现是强信号，但未达到数据库共识阈值时仍只能询问用户，不能直接自动跳过。

不要使用以下单一规则：

- “开头 30 秒都是广告”。
- “所有 discontinuity 都是广告”。
- “所有短分片都是广告”。
- “路径包含 `1000kb` 就是广告”。
- “密钥变化就是广告”。

## 8. 后端接口

后端接口只接收当前播放清单计算出的少量候选指纹，不向前端下发全量广告库。

### 8.1 批量匹配

```http
POST /api/ad-fingerprints/match
Content-Type: application/json
```

必须登录。未登录返回 `401`，前端未登录时本来就不应调用。

请求：

```json
{
  "fingerprints": [
    "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  ]
}
```

约束：

- 数组最多 20 项。
- 去重后查询。
- 每项必须是 64 字符十六进制 SHA-256。
- 空数组直接返回空结果。
- SQL 只查询请求中的指纹，使用主键精确匹配；不得读取全表后在 Go 中过滤。

响应：

```json
{
  "matches": {
    "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef": {
      "status": "confirmed",
      "confirm_count": 5,
      "reject_count": 1
    }
  }
}
```

数据库无记录的指纹可以省略，前端按 `unknown` 处理。

匹配接口发生任何网络、超时、解析或 5xx 错误时，前端必须使用原始播放清单继续播放。

### 8.2 提交投票

```http
POST /api/ad-fingerprints/vote
Content-Type: application/json
```

请求：

```json
{
  "fingerprint": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "vote": "confirm"
}
```

`vote` 只允许：

- `confirm`
- `reject`

要求：

- 必须登录。
- 严格校验 32 字节指纹。
- 使用现有 CSRF 机制。
- 复用 `internal/platform/ratelimit.PerIP` 做投票限流，首版建议每 IP 每分钟最多 30 次。
- 前端同一播放页面内，同一指纹最多提交一次。
- 由于不保存投票明细，后端无法跨会话严格去重；不要增加隐式用户投票表。
- 投票失败不能中断、回退或重新加载视频。

响应返回累加后的两个计数和派生状态，便于当前页面立即更新内存状态。

### 8.3 用户开关

建议共用：

```http
POST /dashboard/settings/ad-skip
```

表单字段：

```text
ad_skip_enabled=on
```

要求：

- 必须登录。
- 复用现有 CSRF 处理。
- `identity.Store` 增加明确的 `UpdateAdSkipEnabled`，不要在 Handler 内拼 SQL。
- 用户设置页和播放页使用同一更新入口。
- 普通表单请求可以重定向回原页。
- 播放页可以用 HTMX `hx-post` 异步提交并替换开关局部，不得重新加载播放器。
- 成功后用 `HX-Trigger` 或一个明确的前端事件通知当前播放器开关已变化。

## 9. 前端播放流程

### 9.1 初始化

`play.html` 和 `watch.html` 调用 `initPlayer` 时增加：

```text
adSkipEnabled: 登录且 UserInfo.AdSkipEnabled
adSkipLoggedIn: 是否登录
loginURL: /auth/login?redirect=<当前完整路径>
```

`initPlayer` 默认把缺失的 `adSkipEnabled` 当作 `false`，这样 `/iptv`、`/player` 和其他调用者不需要修改也不会误启用。

### 9.2 功能关闭

当 `adSkipEnabled` 为 `false`：

- 使用当前 hls.js 加载路径。
- 不安装广告 M3U8 拦截器。
- 不计算指纹。
- 不调用匹配或投票接口。
- 不显示疑似广告或自动跳过提示。

### 9.3 功能开启

当 `adSkipEnabled` 为 `true` 且是 VOD M3U8：

1. 使用 hls.js 自定义 `pLoader` 拦截媒体播放清单文本。
2. 保留原始播放清单文本，供失败开放和“撤销本次”使用。
3. 解析候选块并计算少量 SHA-256 指纹。
4. 一次批量调用匹配接口。
5. 用一次性完成保护包装原 loader 的 `onSuccess`；匹配请求最长等待 250ms。
6. 在时间内返回：仅处理 `confirmed` 且通过本次结构保护的候选。
7. 超时或失败：把原始播放清单交还 hls.js，立即正常播放。
8. 无论匹配、失败、超时、abort 还是 destroy，原 loader 的成功/错误回调都只能完成一次，不能重复交还清单。

只要 `pLoader` 尚未调用原始 `onSuccess`，hls.js 就没有可解析的媒体清单，也不能开始加载其中的媒体分片。因此首版可以保留当前 `autoStartLoad:true` 和 `startFragPrefetch:true`；它们只能在已经收到原文或重写后的清单之后生效。

多码率主播放清单处理：

- 主播放清单没有 `EXTINF`，原样交还，不计算广告候选。
- 选中的 level 媒体播放清单包含 `EXTINF`，在它的 `pLoader` 回调中执行候选分析、批量匹配和 GAP 重写。
- 每一个实际加载的 level 都独立处理；不要把一个码率的候选分片 URI 写进另一个码率的播放清单。

### 9.4 不直接删除媒体行

识别为自动跳过的分片，不要从 M3U8 中物理删除。应在对应媒体 URI 前插入：

```m3u8
#EXT-X-GAP
```

保留原有：

- `#EXTINF`
- 媒体 URI
- `#EXT-X-MEDIA-SEQUENCE`
- discontinuity
- key 变化
- 原时间轴

原因：物理删除分片可能改变隐式媒体序列号、AES IV 推导和时间轴，造成解密错误、音画不同步或中插后卡住。

具体 hls.js 版本必须验证：

- GAP 分片不会发出媒体请求。
- 开头连续 GAP 能从广告结束点开始播放。
- 中间 GAP 不会导致停顿。
- seek、自动换源、重试和销毁流程仍正常。

### 9.5 开头广告

如果 `confirmed` 候选位于开头：

- 播放清单标记 GAP 后，应从第一个可用正片分片开始播放。
- 优先依赖并验证所固定 hls.js 版本的 GAP 跳过行为；只有直接媒体播放清单的测试证明有必要时，才配合显式 `startLoad(adEnd)`。
- 网络面板中第一批媒体请求不应包含广告分片路径。
- 播放开始后显示一次“已跳过广告”淡提示。

### 9.6 中插广告

如果 `confirmed` 候选位于中间：

- 在播放清单解析前标记 GAP，防止缓冲区提前请求广告分片。
- 播放到候选边界时，应越过 GAP 并继续正片。
- 监听播放时间跨越候选区间，只显示一次跳过提示。
- 如果所固定版本的 hls.js 不能稳定跨越 GAP，宁可该候选失败开放，也不要写循环 seek 或高频 `timeupdate` 补丁掩盖卡顿。

### 9.7 未达共识的疑似广告

`unknown` 或 `pending` 的高度疑似候选正常加载和播放。候选真正开始播放时显示非模态确认浮层：

```text
检测到疑似广告 · 26 秒
[是广告，跳过] [不是] [关闭]
```

行为：

- 不暂停视频。
- 不遮挡画面中心、字幕和底部控制栏。
- 点击“是广告，跳过”：立即跳到候选结束位置，并异步提交 `confirm`。
- 点击“不是”：继续播放，并异步提交 `reject`。
- 点击关闭：不投票，本次播放不再询问同一指纹。
- 同一个指纹在本页只显示一次询问。
- 用户确认第一处后，相同指纹在同一播放清单后面再次出现时，本页内可以直接跳过。

第一个确认者必须先看到一部分候选才能判断，因此无法保证其完全不下载广告。这是产品限制，不要通过预先自动跳过未知候选来“优化”。

### 9.8 已确认广告提示

自动跳过时显示低打扰提示：

```text
已跳过 26 秒广告　撤销本次
```

要求：

- 播放器右上角，移动端避开安全区域。
- 约 2 秒后淡出。
- 只使用 150～200ms 的 opacity/轻微 translate 动画。
- 不弹跳、不缩放、不播放声音。
- 支持 `prefers-reduced-motion`，减少动效时只切换 opacity 或无动画。
- 同一次候选只提示一次。

“撤销本次”只恢复当前播放，不自动提交否认票。由于自动跳过候选已经标记 GAP，撤销时允许重新初始化当前 HLS 源：

1. 把该指纹加入当前页面的临时“不跳过集合”。
2. 使用保存的原始播放清单重新加载。
3. 在 manifest 可播放后定位到被跳过候选的开始位置。
4. 不能修改用户的全局开关。

如果撤销恢复失败，保持当前正片继续播放并给出轻提示，不能把播放器留在黑屏或加载状态。

## 10. 开关 UI

### 10.1 用户设置页

在 `/dashboard/settings` 增加“播放设置”区块或导航项，复用现有 Toggle 视觉：

```text
智能跳过广告
开启后自动跳过已确认广告，并询问高度疑似的广告片段；设置会同步到所有设备。
```

开关值直接来自 `.User.AdSkipEnabled`，不从前端本地状态初始化。

### 10.2 播放页

在 `/play` 和 `/watch` 的播放器下方操作区增加紧凑开关。直接服务端渲染，不使用异步 GET。

登录用户：

- 显示当前数据库状态。
- 修改时异步提交，不能刷新或销毁播放器。
- 关闭后立即隐藏待确认浮层并停止后续识别。
- 开启后从下一次换集、换源或重新进入播放页完整生效；不要为了立即应用而重启正在播放的视频。
- 如果当前页面已经完成候选解析，可以只对尚未到达的候选生效，但这不是首版硬要求。

未登录用户：

```text
智能跳过广告
登录后可开启，并在所有设备同步设置
```

- 显示关闭且锁定的开关。
- 点击整行或“登录后开启”进入 `/auth/login?redirect=<当前播放页>`。
- 可以显示一次轻提示“请先登录以开启智能广告跳过”。
- 不要先把开关显示为开启再弹登录框。

## 11. 推荐代码落点

以最少新增抽象为原则，广告功能属于播放链路，后端匹配和投票放在 `internal/playback`，不要为一个实现创建 Service/Factory 层。

建议新增或修改：

```text

internal/identity/postgres.go
internal/identity/handler.go
internal/identity/handler_test.go

internal/playback/adskip_test.go
internal/playback/handler.go

cmd/web/main.go

```

实现建议：

- `playback.Handler` 增加一个最小 `AdFingerprintStore` 依赖和一个投票限流器。
- `playback.NewAdFingerprintPostgresStore(databasePool)` 使用现有数据库连接池。
- 通过一个 `WithAdFingerprintStore` 注入现有 Handler，沿用当前 HandlerOption 模式。
- 不引入 Redis、消息队列、定时任务、后台管理页面或新的前端依赖。
- 用户设置继续由 `identity.Handler` 负责，不要把用户表更新塞进 playback 包。

如果实施时发现放入 playback 包会制造循环依赖，允许建立一个小型 `internal/adskip` 包，但仍然只保留 Store + Handler 所需最小结构，不增加无用 Service 层。

## 12. 安全和失败开放

### 12.1 输入限制

- 指纹只能是 64 字符十六进制，解码后必须恰好 32 字节。
- 匹配数组最多 20 项并去重。
- 投票值必须是固定枚举。
- JSON 使用严格大小限制，不能接受任意大请求体。
- 所有写接口必须登录并经过 CSRF。

### 12.2 限流

- 投票接口使用现有按 IP 限流器，建议 30 次/分钟。
- 前端本页同一指纹只投一次。
- 当前方案不保证独立用户去重；UI 和文案使用“确认次数/否认次数”，不能称为“人数”。

### 12.3 播放优先

以下任何情况都直接使用原始 M3U8：

- M3U8 解析失败。
- 无法可靠识别主体块。
- Web Crypto 不可用或哈希失败。
- 匹配接口超过 250ms。
- 匹配接口返回非 2xx 或格式错误。
- hls.js 不支持当前环境。
- GAP 处理在当前清单类型上不安全。
- 候选超过 120 秒或占据清单主体。

广告功能不能触发自动换源、播放失败上报或播放器 fatal error。

## 13. 数据量和性能约束

### 13.1 后端指纹增长

数据库变大不会直接让前端越来越慢，因为：

- 前端只提交当前播放清单的少量候选。
- 后端只做主键精确查询。
- 不向前端下发全部指纹。
- 不在 Go 或 JavaScript 中扫描完整广告库。

首版不实现布隆过滤器、全量缓存、Redis 或内存热表。只有实际测量证明 PostgreSQL 主键批量匹配成为瓶颈时再增加缓存。

### 13.2 前端性能

- 不下载 TS 计算哈希。
- 只对结构候选计算 SHA-256。
- 使用原生 `TextEncoder` 和 `crypto.subtle.digest`。
- 不使用 Canvas、Web Audio、ffmpeg.wasm 或第三方指纹库。
- 匹配等待有 250ms 硬上限。
- 功能关闭时不产生额外解析、网络和定时器。

### 13.3 缓存

首版只需要当前页面内的 `Set/Map`：

- 已询问指纹。
- 已投票指纹。
- 本页确认指纹。
- 本次撤销指纹。

不要持久化全局“已确认广告”到 `localStorage`，以免数据库票数发生变化后浏览器继续使用过期结论。主键批量查询足够小，持久缓存等真实性能数据出现后再考虑。

## 14. 验收测试

不能只以 `go test` 或编译通过作为完成证据。需要后端测试、播放清单逻辑测试和真实浏览器网络验证。

### 14.1 后端自动测试

至少覆盖：

1. 新用户和迁移后的已有用户 `ad_skip_enabled=false`。
2. 设置开启后重新读取用户为 `true`，其他设备请求能读到相同值。
3. 未登录修改设置返回 401 或登录跳转，不更新数据库。
4. 投票第一次插入和后续原子累加正确。
5. 非法指纹、非法 vote、超长匹配数组被拒绝。
6. `4:0` 返回 `pending`。
7. `5:0` 返回 `confirmed`。
8. `5:1` 返回 `confirmed`。
9. `5:2` 返回 `pending`。
10. `3:5` 返回 `rejected`。
11. 匹配只返回请求中的指纹，不泄露或全量读取其他记录。
12. 投票接口限流生效。

### 14.2 M3U8 解析和指纹测试

把测试文件裁剪成不访问远程媒体的 fixture，建议放入：

```text
internal/playback/testdata/ad_start_and_repeat.m3u8
```

或者为纯前端解析器增加一个无依赖的 Node `assert` 自检脚本。不要为测试引入前端框架。

至少断言：

1. 识别出开头 26.04 秒候选。
2. 识别出约 3536.08 秒处的重复候选。
3. 两处得到相同指纹。
4. 主体块不成为候选。
5. CDN host 和 query 改变后指纹不变。
6. 完整 pathname 改变后指纹改变。
7. 单个 discontinuity 不足以形成候选。
8. 超过 120 秒的块不能自动跳过。
9. 直播或无 `ENDLIST` 清单失败开放。
10. 重写后只增加 `EXT-X-GAP`，没有删除 `EXTINF`、URI 或改变媒体序列。

### 14.3 真实浏览器验收

桌面和 390px 移动端至少各验证一次：

#### 未登录

- 播放器立即正常启动。
- 开关直接显示为关闭和锁定状态，没有 HTMX 初始 GET。
- 点击引导登录并保留当前页 redirect。
- Network 中没有广告匹配和投票请求。

#### 登录但关闭

- 播放行为与修改前一致。
- 不解析、匹配、提示或跳过广告。
- Network 中没有新增匹配请求。

#### 登录并开启，未知广告

- 正常播放候选。
- 候选开始时显示不遮挡字幕的询问。
- 确认后立即跳到候选末尾并异步投票。
- 否认后继续播放且异步投票。
- 关闭后本页不再重复询问。

#### 登录并开启，已确认广告

- `5:0` 和 `5:1` 自动跳过。
- `4:0` 和 `5:2` 不自动跳过。
- 开头广告的 TS 请求不出现在 Network 中，首个媒体请求来自正片路径族。
- 中插广告的 TS 请求不出现在 Network 中，跨越后不卡住。
- 显示“已跳过 26 秒广告”，不遮挡字幕和控制栏。
- “撤销本次”能恢复当前广告或安全失败，不破坏后续正片。

#### 降级

- 人为让匹配接口超时超过 250ms，播放器仍正常开始。
- 匹配接口返回 500、无效 JSON 或断网，播放器仍正常开始。
- 设置接口失败只恢复开关显示，不停止视频。
- 自动换源、下一集、销毁和重新初始化没有遗留计时器或重复提示。

## 15. 完成标准

只有同时满足以下条件才算完成：

- 数据库迁移可重复、可在现有迁移流程中执行。
- 用户设置保存到数据库并跨设备读取。
- 未登录默认关闭且有明确登录入口。
- 播放页开关直接服务端渲染，没有 HTMX 初始加载。
- 功能关闭时播放行为没有变化。
- 自动跳过使用“5 次确认 + 80% 确认比例 + 结构保护 + 120 秒上限”。
- 第一个未知候选只询问，不自动跳。
- 已确认广告分片在真实 Network 面板中没有被加载。
- 任何识别、哈希、接口或 GAP 异常都失败开放。
- `/play` 和 `/watch` 都通过验证。
- IPTV、手动播放器和非 HLS 播放不受影响。
- 固定并验证 hls.js 版本，不再依赖 `@latest`。
- 相关 Go 测试、最小 JS 解析自检和真实浏览器验证都有明确结果。

## 16. 明确非目标

首版不要实现：

- 后端拉取、代理或重写 M3U8。
- TS、视频画面或音频内容感知哈希。
- AI/机器学习广告识别。
- 按电影、集数、资源网或时间保存广告。
- 独立用户投票表。
- Redis、布隆过滤器、全量指纹下发或服务端内存热表。
- 管理后台审核广告。
- 广告统计报表、排行榜或运营看板。
- WebSocket 跨设备实时同步。
- IPTV/直播广告跳过。
- 修改 hls.js、ArtPlayer 或 flv.js 源码。
- 为这项功能新增前端框架或大型依赖。

## 17. 建议实施顺序

1. 增加迁移、用户字段和设置更新，完成账号设置页与播放页直接渲染。
2. 增加指纹 Store、批量匹配、投票、阈值计算和后端测试。
3. 将 M3U8 解析、候选检测、规范化和 SHA-256 写成纯函数并用 fixture 验证。
4. 接入固定版本 hls.js 的 `pLoader`，先完成超时失败开放。
5. 实现 `EXT-X-GAP` 自动跳过，验证开头和中插媒体请求确实未加载。
6. 实现未知候选询问、投票、淡提示和撤销本次。
7. 验证 `/play`、`/watch`、桌面、390px 移动端、自动换源和下一集。
8. 最后运行完整 Go 测试和真实浏览器网络检查，记录实际结果。

实施者应优先保证“不误跳正片”和“任何异常不影响播放”，其次才是尽可能少加载广告分片。

## 18. 官方实现依据

- [hls.js API：`pLoader`、`autoStartLoad` 和 `startLoad`](https://github.com/video-dev/hls.js/blob/master/docs/API.md)
- [hls.js README：支持 `EXT-X-GAP` 并跳过 GAP 分片加载](https://github.com/video-dev/hls.js/blob/master/README.md)
- [IETF HLS 2nd Edition 草案：`EXT-X-GAP` 只作用于下一个媒体分片，客户端不应加载该 URI](https://datatracker.ietf.org/doc/draft-pantos-hls-rfc8216bis/)

插入 GAP 时，将 `#EXT-X-GAP` 放在目标媒体分片的标签序列中、对应 URI 之前，并保持该分片的 `EXTINF` 和 URI。规范把一个媒体分片定义为一系列 Media Segment Tags 后跟 URI；不要把 GAP 放到目标 URI 之后，否则会作用于下一个分片。
